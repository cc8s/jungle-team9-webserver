# 아키텍처 의사결정 과정

## F1_processhttp

이 문서는 최종 기능 목록이 아니라 **어떤 문제에서 어떤 선택지를 검토했고, 사용자가 무엇을 선택했으며, 무엇을 얻고 감수했는지** 기록한다. 최초 HTTP 설계부터 POST 확장, GET 모듈 분리, Persistent Connection까지 F1의 흐름을 다룬다. 이 절은 F1을 다루며, F2의 신규 설계와 미결정 항목은 뒤의 F2_multithread 절에 별도로 기록한다.

대화에서 확인되는 사용자 선택과, 저장소에만 남아 있는 후속 변경을 구분한다. 트레이드오프는 선택의 기술적 의미를 정리한 것이며, 전부 사용자가 당시 직접 말한 동기라는 뜻은 아니다. 폐기한 초기 정책을 현재 정책과 혼동하지 않는다.

현재 계약과 함수·테스트 목록은 각각 [F1 설계](F1_processhttp/f1_design.md), [함수 흐름](F1_processhttp/f1_funcflow.md), [테스트 케이스](F1_processhttp/f1_testcases.md), [연결 재사용 설계](refactor_persistentCon.md)를 참조한다.

### 1. 처음에는 HTTP의 경계를 이해하는 데서 시작했다

사용자는 CRLF로 행을 나누고, 요청 경로와 헤더를 추출한 뒤 open/read로 파일을 읽어 응답하는 흐름을 제시했다. 논의 과정에서 다음은 선택 가능한 정책보다 먼저 지켜야 하는 프로토콜·I/O 조건으로 정리됐다.

- 한 번의 read/recv가 한 행 또는 요청 전체와 일치하지 않는다.
- CRLF 두 개는 헤더의 끝이다. 본문 전체의 끝은 Content-Length 등 별도 길이 정보로 판단한다.
- 요청 Content-Type은 요청 본문의 형식이고, 정적 응답 MIME은 서버가 실제 제공하는 파일을 기준으로 정한다.
- 응답은 상태 라인 → 헤더 → 빈 줄 → 본문 순서다. 시스템콜을 반드시 네 번 호출한다는 뜻은 아니다.
- 부분 읽기·쓰기를 처리하고 바이너리 본문의 길이를 strlen으로 계산하지 않는다.

이 이해를 바탕으로 실제 구현 정책을 결정했다.

### 2. 학습 방식과 구현 단위부터 다시 정했다

| 논점 | 제안·대안 | 사용자 결정 | 이점과 감수한 점 |
|---|---|---|---|
| 한 번에 구현할 범위 | 파서·정적 파일·응답·시간 제한을 한 번에 구현 | 첫 대규모 구현을 롤백하고 기존 코드에서 확장 | 원래 코드와 호출 흐름을 따라갈 수 있음. 완성까지 여러 작업과 검증이 필요 |
| 작은 단계의 크기 | 수신 관찰 → 누적 → 요청 라인 등 세부 단계별 구현 제안 | A: HTTP request 파싱 / B: HTTP response 생성·쓰기로 나눔 | 기능 경계가 분명해짐. 단순히 한 줄씩 추가하는 수준보다 각 단위의 변경량은 커짐 |
| 구현 전 합의 | 에이전트가 세부 구조를 정하고 구현 | 미결정 동작·구조는 구현 전 합의 | 예기치 않은 변경을 줄임. 질문이 반복되면 작업 흐름을 방해하므로 이미 결정한 항목은 재질문하지 않아야 함 |
| 산출물 | 단일 설계 문서 | 기능 디렉토리에 design/funcflow/testcases 작성 | 정책·흐름·검증을 나눠 검토 가능. 구현 후 문서 간 정합성 관리 필요 |
| 롤백 지점 | 작업 종료 시 변경만 남김 | 작업 단위마다 Git 커밋과 해시 보고 | 특정 작업으로 돌아가기 쉬움. 기존 사용자 변경을 섞지 않도록 선택 스테이징 필요 |

이 과정에서 “코드를 완성하는 것” 외에 “기존 코드에서 기능이 확장되는 이유와 흐름을 이해하는 것”이 작업 목적임을 명확히 했다. 이후 서브 에이전트 구현도 이 기준과 문서 계약을 따르도록 요청했다.

관련 기록: `6160ded` 작업 규칙, `f21ab2e` 문서 분리, `55fe92e` A, `6d7aa11` B.

### 3. 요청 수신·파서·오류의 책임을 나눴다

| 논점 | 제안·대안 | 사용자 결정 | 이점과 감수한 점 |
|---|---|---|---|
| 파서와 소켓 수신 | 파서에서 직접 read / 버퍼를 받아 해석 | 수신과 파서를 분리 | 소켓 없이 파서를 시험할 수 있음. 호출자가 누적과 재호출을 관리해야 함 |
| 파싱 결과 | 성공·실패만 반환 / 부족·완료·오류 구분 | 부족·완료·오류 및 소비 범위 전달 | 분할 수신과 비정상 입력을 구분. 상태·길이 관리가 추가됨 |
| 필드 보관 | 문자열 복사 / 버퍼 포인터 / 오프셋·길이 | 오프셋·길이 | realloc 뒤에도 유효하며 복사를 줄임. 접근 시 범위 검사와 버퍼 수명 관리 필요 |
| 버퍼 확장 | 고정 크기 / 동적 확장 | 4 KiB부터 확장, 요청 라인 8 KiB·헤더 32 KiB·본문 1 MiB 상한 | 작은 요청에 적은 초기 메모리 사용. 확장 비용과 상한 초과 처리가 필요 |
| 버퍼를 비우는 시점 | 파싱할 때마다 비우기 / 요청 처리 완료까지 유지 | 처음에는 응답 완료 후 해제 | 헤더와 함께 도착한 본문을 보존. 응답까지 버퍼가 메모리에 남음. 이후 연결 단위 유지로 변경 |
| 잘못된 본문 길이 | 관대하게 해석 / 잘못된 값·중복 거절 | 잘못된 숫자·음수·오버플로우·중복은 파싱 오류 | 해석이 단순하고 모호한 경계를 거절. 동일한 길이의 중복도 허용하지 않음 |
| 전송 코딩 | chunked 지원 / 초기 범위에서 거절 | 단독 Transfer-Encoding 미지원, Content-Length 병용은 문법 오류 | 초기 파서 범위를 제한. chunked 클라이언트는 처리할 수 없음 |
| A/B 오류 전달 | 파서가 HTTP 상태 코드를 직접 결정 / 오류 종류 전달 | A는 오류 종류, B는 상태·응답 생성 | 파싱과 전송 책임 분리. 명시적 오류 매핑 필요 |

“flush”에 대한 질문에서는 파싱이 메모리의 바이트를 자동으로 없애지 않는다는 점을 확인했다. 처음에는 버퍼를 끝까지 유지·해제하는 정책이었고, 연결 재사용 이후에는 요청별 소비와 연결별 해제로 발전했다.

### 4. 타임아웃 수단은 임시 조치에서 소켓 모드 변경으로 발전했다

| 논점 | 제안·관찰 | 사용자 결정 | 이점과 감수한 점 |
|---|---|---|---|
| 수신·쓰기 시간 | 최초 헤더 10초·본문 30초·쓰기 10초 제안 | 로컬 테스트에 맞춰 헤더 5초·본문 10초·쓰기 5초 | 실패를 빨리 관찰. 느린 클라이언트에는 엄격한 제한 |
| 기한 시작 | 연결을 기다리는 시간까지 포함할 가능성 | 헤더는 accept 성공 직후부터 | accept의 연결 대기와 요청 수신 대기를 구분 |
| 전체 기한·재시도 | 바이트마다 기한 연장 / 고정 기한 | 헤더·본문은 연장하지 않음 | 조금씩 보내며 무기한 점유하는 상황을 제한. 느린 정상 요청도 종료될 수 있음 |
| 쓰기 기한 | 응답 전체 5초 / 진행 없이 5초 | 마지막 양수 send 이후 5초 | 큰 파일도 계속 진전하면 전송 가능. 전체 응답 시간을 제한하는 정책은 아님 |
| 초기 구현 범위 | 시간 제한 수단도 즉시 결정 / 보류 | 첫 A 구현에서 수단 보류와 블로킹 소켓 유지 승인 | 파싱 구조부터 구현. 그 시점 A에는 무한 대기 가능성이 남아 있었음 |
| 시간 제한 보완 | 헤더/본문 미완료 상태를 그대로 둠 / 대기 기한 추가 | 헤더 5초부터 보완, 이후 본문 10초 적용 | 미완료 범위가 명확해짐. 초기 “A 완료” 보고는 시간 제한까지 완료한 의미로는 부정확했음 |
| 쓰기 정체 임시 대응 | MSG_DONTWAIT로 16 KiB 전송 시 테스트가 멈춤 | 사용자가 사전에 선택한 정책은 아님. 에이전트가 1 KiB 제한으로 우회한 뒤 상황을 설명 | 해당 테스트 정체를 피했지만 근본 원인은 미규명. 크기 제한만으로 비차단 보장을 대체할 수 없음 |
| 최종 소켓 모드 | 호출별 MSG_DONTWAIT 유지 / conn_fd 자체 O_NONBLOCK | sock_fd는 블로킹, conn_fd는 O_NONBLOCK + poll | 부분 전송·EAGAIN을 공통 패턴으로 처리하고 1 KiB 제한 제거. 모든 수신·전송 경로가 재시도를 처리해야 함 |

초기 정체는 작은 송신 버퍼의 테스트에서 send 호출이 돌아오지 않는 것으로 관찰됐다. 당시 MSG_DONTWAIT 동작의 근본 원인까지 규명한 것은 아니다. “요청 크기가 송신 버퍼보다 크면 전송 자체가 불가능하다”는 해석 대신, 논블로킹 부분 전송과 반환값 기반 처리를 채택했다.

관련 기록: `287ec08` 헤더 기한, `9cc55bf` 본문 기한, `9e83dfd` 모드 계약, `2755275` 논블로킹 적용.

### 5. GET 본문 정책은 세 번 바뀌었다

| 단계 | 제안·사용자 선택 | 그때의 이유와 트레이드오프 | 이후 변화 |
|---|---|---|---|
| 최초 | GET도 Content-Length만큼 받은 후 본문을 사용하지 않음 | 메서드와 무관하게 전체 요청 경계를 확인. 정적 파일 응답에는 필요 없는 본문도 기다림 | 사용자가 GET이 굳이 대기해야 하는지 질문 |
| 연결당 한 요청 | GET은 헤더 검증 후 즉시 응답, POST만 본문 수신 | GET 지연 감소. 응답 뒤 연결을 닫으므로 다음 요청 경계 보존 부담이 작음 | Persistent Connection 도입으로 그대로 유지할 수 없게 됨 |
| 연결 재사용 | 사용자가 “바로 응답하고 연결 유지” 선택. 남은 본문을 응답 후 폐기하는 방식까지 확인·승인 | 빠른 GET 응답과 재사용을 함께 확보. 본문 폐기 상태·10초 기한·바이너리 경계 관리가 필요 | 현재 정책 |

현재 GET의 파서 완료 지점은 여전히 헤더다. 응답 후 정확히 Content-Length 바이트를 제거하고 다음 요청을 보존한다. 폐기 실패 시 이미 응답했으므로 추가 408/500 없이 연결을 닫는다.

### 6. 정적 파일·응답 처리에서 경계와 안전성을 정했다

| 논점 | 제안·대안 | 사용자 결정 | 이점과 감수한 점 |
|---|---|---|---|
| URI 처리 순서 | 경로를 바로 파일명으로 사용 / 전처리 후 접근 | 쿼리 분리 → 한 번 디코딩 → 검증 | 쿼리와 경로를 구분하고 인코딩된 경로 이탈 검사 가능. 전처리 순서 유지 필요 |
| 파일 경로 | 마지막 파일명만 추출 / 전체 하위 경로 유지 | 정적 루트 안의 전체 경로 유지, 루트 밖 차단 | CSS 등 하위 경로 지원. 경로 요소 단위 검사 필요 |
| 심볼릭 링크 | 허용 / 차단 | 중간·최종 링크 모두 차단 | 루트 밖 링크 접근 방지. 정상적인 링크 배치도 사용할 수 없음 |
| 파일 접근 | 문자열 결합만 사용 / 디렉토리 FD 기준 접근 | openat/O_NOFOLLOW, 일반 파일 확인 승인 | 파일 접근 제약을 시스템콜에도 반영. 구현과 FD 정리가 늘어남 |
| 기본 파일·루트 | 설정 외부화 / 초기 고정 정책 | www, `/`는 index.html, 다른 디렉토리는 403 | 초기 실행과 동작이 단순. CLI·설정으로 루트를 바꾸는 기능은 별도 필요 |
| 응답 MIME | 요청 타입을 복사 / 파일 확장자 매핑 | 실제 파일의 확장자로 결정 | 정적 파일마다 일관된 타입 제공. 내용 자체의 형식 검증은 아님 |
| 응답 도중 실패 | 새 500을 덧붙임 / 연결 종료 | 설명 후 자원 정리·연결 종료 선택 | 이미 보낸 응답을 오염시키지 않음. 클라이언트는 불완전 응답으로 실패를 판단 |
| 문법·길이 오류 우선순위 | 제한 안 문법 오류, 초과 영역은 길이 오류 우선 제안 | 사용자가 문법 오류 우선 선택 | 수신된 데이터의 문법 오류를 우선 보고. 누적 상한이 있으므로 아직 받지 않은 오류까지 기다리지는 않음 |
| 응답 API의 범위 오류 | 검증 없이 필드 참조 / 경계 검사 | 내부 구조체 범위 오류 500, 유효 범위의 과도한 URI 414 | 스택 오버플로우·오버리드 방어. 호출 계약 검사가 추가됨 |
| 소스 배치 | GET 처리를 http_response.c에 유지 / POST처럼 분리 | 사용자가 http_get.c 분리 요청 | 메서드별 흐름이 드러남. 공통 전송 함수와 파일 FD 소유권 계약 필요 |

관련 기록: `a54e873` 경계·우선순위 보완, `97123f1` GET 분리.

### 7. POST는 echo 제안에서 구조화 데이터와 파일 저장으로 확장됐다

| 논점 | 제안·대안 | 사용자 결정 | 이점과 감수한 점 |
|---|---|---|---|
| 최초 POST 기능 | /echo로 받은 바이트 반환 | JSON·폼 해석을 선택 | 실제 구조화 요청 처리를 학습. 파서·직렬화·복잡도 제어 필요 |
| 경로 분리 | 모든 POST를 같은 처리로 연결 / 경로별 분기 | /api/users, /api/form, /api/upload 제안 승인 | 역할과 허용 타입이 명확. 예약 API와 정적 경로 우선순위 필요 |
| 응답 타입 | 요청 타입 재사용 / 공통 JSON 결과 | 공통 application/json 응답으로 설계 진행 | 클라이언트가 한 응답 형식을 다룸. 문자열 이스케이프·바이트 길이 계산 필요 |
| JSON 파서 | 라이브러리 / 직접 구현 | 직접 구현 | C로 문법·메모리 관리를 학습. UTF-8·중첩·숫자·오류 복구 구현 부담 증가 |
| 복잡도 | 크기만 제한 / 구조별 상한 추가 | 깊이16, 객체100, 배열1,000, 전체값10,000, 폼100, 본문1 MiB 승인 | 자원 소모 상한이 명확. 상한을 넘는 정상 형식 데이터도 413 |
| 문자열·숫자 | C 문자열·double 중심 / 길이 기반 문자열·숫자 원문 | UTF-8 바이트+길이, 검증한 숫자 원문 보관 승인 | NUL과 큰 정수 정밀도 보존. 길이·유니코드 검증과 타입별 처리 필요 |
| 중복 키·필드 | 첫 값·마지막 값·배열 / 거절 | 중복 JSON 키·디코딩된 폼 필드명을 400 | 해석 모호성 제거. 동일 이름 다중 선택 폼은 지원하지 않음 |
| 요청 길이 | 누락을 0과 동일 처리 / 명시적 길이 필수 | POST 길이 누락은 411 | 프레이밍 요구가 명확. 누락·0을 구분하는 상태 필요 |
| Content-Type | 매개변수 무시 / 제한된 문법 지원 | 없음 또는 charset=utf-8만 허용, 중복400·다른 매개변수415 승인 | 초기 호환 범위를 명확히 제한. 다른 charset·확장 매개변수는 처리하지 않음 |

#### 빈 POST 본문은 초기 선택과 후속 변경을 구분한다

대화에서는 명시적인 Content-Length: 0을 허용하고 길이 누락만 411로 거절하도록 선택했다. 이후 사용자가 세 API 모두 본문이 필요하다고 지적하고, 빈 본문을 400으로 거절하는 정책을 선택했다(`67635f3`). **현재 문서·코드는 후자**다.

후속 대화에서 확인한 제안·선택 과정은 14절에 추가했다. 초기 허용 결정과 이후 거부 결정을 구분한다. 빈 HTTP 본문과, 유효한 업로드 JSON 안의 빈 Base64 data로 만드는 0바이트 파일은 별개다.

관련 기록: `9c0d01f` POST 설계, `57e616c` JSON·폼 파서, `9310980` POST 구현.

### 8. 파일 업로드는 multipart 대신 Base64 JSON으로 결정했다

| 메타데이터 | 응답에만 포함 / 별도 보관 | 같은 ID의 .bin + .json | 바이트와 원본명·타입·크기를 분리 보존. 두 파일 생성·정리가 필요 |

파일은 생성 시0600으로 기록한 뒤 두 파일 모두0400으로 바꾼다. 이 권한·일반 실패 정리는 프로세스 강제 종료나 전원 장애에도 파일 쌍이 원자적으로 보존된다는 뜻은 아니다. fsync 기반 내구성·원자적 커밋은 보장 범위 밖이다.

파일명·타입을 JSON에 함께 보내는 이유도 이 단계에서 정리했다. 외부 application/json은 요청 포맷이고 JSON의 content_type은 파일 메타데이터다. 서버는 이를 근거로 형식 변환하지 않는다.

관련 기록: `5b5d3b3` 저장·권한·Base64 계약, `9310980` 구현. 테스트 도구는 [upload_fixture.py](../tests/tools/upload_fixture.py)다.

### 9. 테스트는 기능 추가에서 계약 검증으로 확장됐다

처음에는 구현된 주요 흐름과 회귀 테스트를 실행했지만, 설계 문서의 모든 계획을 자동 테스트로 만들지는 않았다. 사용자는 “실행 안 해봤는지”, “왜 미실행인지”를 확인하고, 기능별로 흩어진 항목을 하나의 표로 재편하도록 요청했다.

| 논점 | 검토·문제 | 사용자 결정·요청 | 이점과 감수한 점 |
|---|---|---|---|
| 결과 표현 | 계획표는 미실행인데 하단에는 통과 기록이 존재 | 카테고리·테스트 코드·설명·통과여부의 단일 표 | 실제 상태를 찾기 쉬움. 자동·수동·부분 검증을 지속적으로 갱신해야 함 |
| 미실행 항목 | 작성 누락과 환경·도구 제약이 섞임 | 미실행 이유 확인 | 구현 누락과 재현 제약을 분리. 통과 수만으로 완성도를 판단하지 않음 |
| 검증 범위 | 정상 요청 위주 / 경계·오류·실패 주입 | 이후 저장소에서 테스트 보강 진행 | syscall 실패·경계·저장 복구까지 확인. 주입 모델과 실제 OS 동작의 차이는 남음 |

단일 표 재편은 `2c9f314`다. 후속 검증 기록에는 MIME·라우팅·Host·파일 실패·타임아웃·시각 충돌·자원 계측 보강이 있다. 이는 커밋에서 확인한 작업 이력이며, 이 대화에 없는 개별 선택까지 사용자 발언으로 추정하지 않는다.

특히 과거 API의 Linux·안정성 검증과, 이후 추가된 Persistent Connection 경로의 Linux·장기 재사용 검증은 같은 결과로 합치지 않는다. 테스트에서 관찰한 부분 파일을 저장 원자성의 성공으로 기록하지 않는다.

### 10. Persistent Connection에서는 사용자가 제안과 다른 조합을 선택했다

처음에는 연결당 요청 하나·Connection: close를 채택해 파서를 단순하게 구현했다. 이후 사용자가 TCP 소켓을 재사용하고 싶다고 요청하면서 연결 수명과 요청 수명을 분리했다.

| 논점 | 제안·대안 | 사용자 선택 | 이점과 감수한 점 |
|---|---|---|---|
| 연결 처리 위치 | main 안 반복문 / handle_connection 추출 | 초안의 연결 함수 분리 흐름으로 진행 | 초기화와 연결 수명이 분리. 기존 코드에서 진입 함수가 하나 추가됨 |
| 버퍼 소비 | memmove / 읽기·쓰기 오프셋 | memmove | 처음 구현을 이해하기 쉬움. 남은 데이터 복사 비용 발생 |
| GET 본문 | 전부 받고 응답 / 본문 있으면 응답 후 종료 제안 | 즉시 응답하고 유지 요청. 추가 설명 후 응답 뒤 정확한 본문 폐기 승인 | 첫 응답 지연을 줄이고 재사용 가능. 폐기 단계와 기한·경계 처리가 추가됨 |
| 오류 이후 | 모든 오류 종료 / 경계를 아는 오류만 유지 | 모든 오류 응답 후 종료 | 복구·재동기화가 단순. 404 같은 애플리케이션 오류에도 새 연결 필요 |
| 유지 응답 헤더 | Connection: keep-alive 명시 제안 / 생략 | 생략 선택 | HTTP/1.1 기본 지속 연결 의미 사용. 종료할 경우에는 명시적 close 필요 |
| 유휴·요청 수 | 유휴5초·최대100개 제안 | 추천안 승인 | 점유 시간·요청 수 제한. 정상 클라이언트도 제한에 도달하면 재연결 필요 |
| 다음 헤더 기한 | 수신 시각 추적 / 처리 시작 기준 | 이미 버퍼에 있는 요청은 처리 시작부터5초 | 요청별 수신 시각 저장 불필요. 큐에 머문 시간까지 제한하는 정책은 아님 |
| 동시성 | 연결 재사용만 / 연결 간 병렬 처리 포함 | 이번에는 재사용만 | 변경 범위를 제한. 한 연결의 유휴·처리 중 다른 accept가 지연됨 |

초기 선택지의 “옵션 B”는 본문 있는 GET의 응답 후 종료였지만, 사용자는 “바로 응답하고 연결 유지”라고 수정했다. 이를 단순히 B안 승인으로 취급하지 않고, **응답 → 본문 폐기 → 다음 요청**으로 다시 설명해 합의했다.

확정 시간은 첫 헤더 accept부터5초, 다음 유휴5초, 다음 헤더 첫 바이트 또는 버퍼 요청 처리 시작부터5초, POST 본문10초, GET 응답 후 폐기10초, 쓰기 진행 없음5초다. 100번째 응답에는 close를 명시한다. 유휴 만료는 무응답 종료, 요청 중 수신 기한 초과는 가능한408 응답 후 종료, 응답 후 폐기 실패는 추가 응답 없이 종료다.

구현에서는 실제 서버가 http_respond의 전송 결과·종료 여부를 사용하고 기존 http_send_response는 단일 응답 호환 API로 남겼다. 이는 에이전트의 구현 선택이며 사용자가 별도로 고른 옵션은 아니다. 기존 직접 응답 테스트를 유지하는 대신, 실제 연결 반복은 Content-Length 기반 신규 테스트와 독립 TCP 테스트로 확인한다.

관련 기록: `e3124bf` 설계, `88a3680` 구현, `cd4c3fe` 검증·문서.

### 11. 사용자 선택의 확인 범위

Host 정책은 기존 기록으로 확인한다. POST 입력 검증은 이후 사용자가 직접 내린 결정 과정이 추가로 확인되어 14절에 상세히 기록했다.

| 정책 | 확인 근거 | 기술적 의미 |
|---|---|---|
| Host B안: 이름·IPv4·대괄호 IPv6·포트 검증 | `630c2a9`, F1 설계 | 단순 Host 존재 검사보다 엄격함. 전체 RFC reg-name/IPvFuture/zone ID 지원은 아님 |
| 명시적 빈 POST 본문400 | `67635f3`, 14절 사용자 결정 | 초기 0길이 허용 정책을 대체. 누락411 및 업로드0바이트 파일과 구분 |
| 업로드 빈 content_type·폼 NUL 거절 | `71f367f`, 14절 사용자 결정 | JSON/파일의 NUL 보존과 폼 입력 제약을 구분 |
| 폼 빈 세그먼트 무시·빈 키 거절 | `b18a54f`, `3f500a2`, 14절 사용자 결정 | & 반복은 무시하되 =value 같은 빈 키는400. 키만 있는 항목은 빈 값으로 처리 |

### 12. F1에서 남은 경계

F1은 요청 프레이밍, 응답 전송, 정적 파일, POST 파싱·저장, 연결 재사용까지 확장됐다. 다만 다음을 자동으로 해결한 것은 아니다.

- 고정 www·포트의 설정 외부화와 연결 간 동시 처리.
- 업로드 다운로드 API, 중복 제거, 저장 파일 형식 검증, 전원 장애까지 포함한 원자성·내구성.
- 모든 플랫폼과 모든 신규 경로의 동일한 검증. 실행 결과는 테스트 표의 개별 범위를 따른다.

이후 기능에서는 이 문서의 과거 선택을 그대로 복사하기보다, 조건이 바뀌었는지 확인한 뒤 계약을 변경한다. 예를 들어 GET 본문을 무시하던 정책은 연결당 한 요청에서는 단순했지만, 연결 재사용에서는 폐기 책임까지 추가해야 했다.

### 13. 초기 A/B 설계의 선택 순서와 확인 근거

아래는 초기 대화에서 직접 확인한 결정 과정이다. 앞 절의 주제별 정리를 보완하는 이력이며, 이후 변경된 정책을 현재 계약으로 되돌리는 지시가 아니다. 사용자 발언의 짧은 인용은 선택 근거이고, 트레이드오프는 그 선택의 기술적 영향이다.

| 순서·상황 | 에이전트가 제안한 옵션 | 사용자 선택·확인 근거 | 당시의 트레이드오프 |
|---|---|---|---|
| 1. 원래 코드와 학습 흐름이 사라짐 | 요청·파일·응답·시간 제한을 한 번에 구현 | “일단 롤백해”, “원래 코드 기준으로 기능이 조금씩 확장되면서 이해하는게 목적” | 구현 속도보다 변경 이유와 호출 흐름의 이해를 우선. 이후 작업마다 설명·검증이 필요 |
| 2. 지나치게 잘게 나눈 구현 제안 | read 관찰부터 세부 단계별로 확장 | “A: Http request 파싱 / B: Http response 생성 (쓰기)” | 수신 관찰만으로 작업을 끊지 않고 기능 책임으로 나눔. 각 단위 내부에는 여러 함수와 테스트가 필요 |
| 3. 초기 기능 범위 | GET 정적 응답 우선, POST는 이후 | “1 예. Post 는 나중에.” | 정적 응답부터 이해 가능. POST는 별도 확장까지 미지원 |
| 4. 연결 정책 설명 요청 | 한 연결에서 여러 요청 처리 / 첫 요청 후 close | keep-alive와 연속 요청 예시 설명 후 “지금 단계에서는 첫 요청만 처리하기” | 남은 요청의 버퍼 이동·재사용 루프를 제외. 파일마다 재연결 비용 발생. 이후 Persistent Connection에서 변경 |
| 5. 수신 버퍼를 비우는 시점 질문 | 파싱 시 비우기 / 응답까지 보존 | flush 의미 설명 후 응답 완료까지 유지·연결 정리 시 해제에 “네” | 헤더와 동시에 받은 본문, 버퍼를 참조하는 필드를 보존. 응답 전송 중에도 수신 메모리를 유지 |
| 6. 버퍼와 상한 | 고정 확보 / 4 KiB부터 확장, 라인8 KiB·헤더32 KiB·본문1 MiB 제한 | 크기 제한 제안에 “네” | 초기 메모리는 작게 유지. 확장 실패·상한 오류 처리가 추가되고 큰 요청은 거절 |
| 7. GET 본문 무시의 의미 질문 | 헤더만 받고 응답 / Content-Length까지 받아 사용하지 않기 | “Content-Length 까지만 읽는다는거임? 일단 이 방식으로 결정.” | 최초에는 전체 요청 경계를 확인하는 일관성을 선택. 불필요한 GET 본문 대기 비용이 있었으며 이후 정책 변경 |
| 8. A 구현 직전 남은 항목 일괄 합의 | 오프셋·길이, 잘못된·중복 길이 거절, TE 단독 미지원·CL 병용 오류, 오류 종류를 B에 전달, 시간 제한 수단 보류 | 묶음 제안에 “제안대로 A 구현” | 메모리 복사와 A/B 결합을 줄임. 필드 접근·오류 변환이 필요하고, 당시에는 무한 대기 가능성이 남음 |
| 9. 헤더 기한 누락 지적 | 타임아웃 수단 보류 상태 유지 / A에서 수신 기한 보완 | accept 이후라는 기준을 확인하고 “헤더 수신 타임아웃 부분도 마저 구현해” | accept 성공부터5초 고정 기한 적용. 느린 정상 요청도 종료 가능. 그 단계에서는 본문10초는 여전히 미구현 |
| 10. B 정책과 쓰기 제한 이해 | www·index.html·디렉토리403, openat/O_NOFOLLOW, 오류 매핑, poll/send 호출별 비차단과 쓰기5초 | 처음에는 “정책 수정 후 구현” 선택 뒤 4번 설명 요청. 전체5초가 아닌 진행 없는5초 설명 후 “오케이 그렇게 하기” | 정적 접근과 오류 동작을 고정하고 소켓 모드는 유지. 전송이 계속 진전하면 전체 응답 시간은5초를 넘어도 됨 |

초기 타임아웃 수치는 헤더10초·본문30초·쓰기10초 제안에서 사용자가 로컬 테스트에 맞춰 **5초·10초·5초**로 변경했다. 헤더·본문은 전체 기한, 쓰기는 마지막 전송 진전부터의 기한으로 구분했다. 사용자 확인 없이 완료 범위를 넓혀 해석하지 않는다.

#### 결정과 구현 조치를 구분할 사례: 1 KiB send 제한

- **관찰:** 작은 송신 버퍼와 읽지 않는 상대를 둔 테스트에서 poll은 쓰기 가능을 반환했지만, 16 KiB send 호출이 돌아오지 않는 것으로 관찰됐다.
- **에이전트 조치:** 한 번의 send를 최대1 KiB로 제한했고 같은 테스트의5초 종료를 확인했다. 이 제한은 사전에 제시해 사용자가 선택한 설계 옵션이 아니다.
- **당시 한계:** MSG_DONTWAIT인데 대기한 근본 원인은 규명하지 못했다. 해당 테스트 통과를 모든 환경의 비차단 보장으로 일반화할 수 없다.
- **사용자 확인:** 사용자는 이슈 상황 설명을 요청했고, 에이전트는 우회 조치와 근본 원인 해결을 구분해 설명했다. 설명을 요청한 것을 우회 조치의 별도 승인으로 기록하지 않는다.
- **후속 정책:** 연결 FD의 O_NONBLOCK 전환 및 제한 제거 이력은 4절에 따로 기록돼 있다. 초기 합의인 소켓 모드 유지와 구분한다.

초기 결정의 브레이크포인트: `ef47dc7` GET·첫 요청·A/B 단위, `cb132f1` 버퍼 크기, `cd6d38b` 버퍼 수명·GET 본문, `55fe92e` A 구현, `287ec08` 헤더 기한, `6d7aa11` B 구현. 문서의 후속 정책과 비교할 때는 해당 시점의 범위를 기준으로 읽는다.


### 14. POST 입력 검증과 업로드 ID를 다시 검토했다

사용자는 빈 본문, 업로드 메타데이터, 폼 빈 세그먼트와 NUL, 공유 순번의 동시성 문제를 제시했다. 처음에는 원인 조사를 요청했지만, 곧 직접 정리한 원인·맥락을 제공하고 별도 조사는 생략하도록 변경했다. 아래는 그 이후 대화에서 확인한 제안과 선택이다. 사용자 항목 번호가 대화 중 바뀌었으므로 주제명으로 구분한다.

#### 입력 검증: 초기 제안부터 최종 정책까지

| 상황 | 에이전트가 제안한 옵션·설명 | 사용자 선택·확인 근거 | 이점과 감수한 점 |
|---|---|---|---|
| 빈 HTTP 본문이 검증을 우회해 200 | 모든 POST API에서 400 / upload만 400. 초기에는 기존 설계의 명시적 0 허용을 버그처럼 설명했으나 문서 확인 후 정정 | users·form·upload 모두 본문이 필요하므로 0이면 오류가 맞다고 판단. 200 분기를 오류로 바꾸고 문서·테스트도 수정하는 범위에 “이렇게 결정” | 세 API에서 검증 의미가 일관됨. 기존 빈 요청 성공 계약은 깨짐. 경로 확인 후 Content-Type 검사보다 먼저 400 invalid_body, 길이 누락은 411 유지 |
| 업로드 JSON의 빈 content_type | 빈 문자열은 400 권장. HTTP 헤더 Content-Type과 JSON 메타데이터 필드의 차이를 예시로 설명 | “content_type 빈값 허용X 에러로 핸들링” | 메타데이터 타입이 미지정인 업로드를 저장하지 않음. 비어 있지 않은 문자열의 MIME 문법·실제 파일 형식까지 검증하는 것은 아님 |
| 폼의 NUL 바이트 | NUL만 차단 / 다른 제어 문자까지 차단을 제안. JSON 직렬화가 깨지는 문제와 입력 정책 문제를 구분 | “NUL 바이트 허용 X 에러로 핸들링”을 폼 디코딩 범위에 적용 | 폼 키·값의 원문 0x00과 %00을 400으로 거부. JSON의 이스케이프된 NUL과 업로드 바이너리 NUL은 보존. 나머지 제어 문자 일괄 차단은 선택하지 않음 |
| & 위치에 따라 빈 필드가 생성됨 | 빈 조각 모두 무시 / 모두 400. 최초에는 무시 권장, 사용자가 이유를 물은 뒤 관대한 처리와 엄격한 처리 모두 타당함을 설명 | “무시 and 버리기 방향으로 선택.” 원문을 &로 나누고 빈 조각은 continue한 뒤 비어 있지 않은 조각만 =로 분리하는 흐름을 직접 지정 | 선행·중간·후행 &를 일관되게 처리하고 불필요한 빈 필드를 만들지 않음. 반복 구분자를 오류로 탐지하지 않으며, &만 있는 양수 길이 본문은 200과 빈 객체 |
| = 없는 foo의 처리 | 전체를 키, 값은 빈 문자열로 처리하는 기존 동작 유지 | 사용자가 제시한 처리 흐름에 명시. 이후 a=1&foo 예시로 확인 | 값이 없는 필드도 표현 가능. = 누락을 잘못된 입력으로 거부하지 않음 |
| =foo처럼 키가 없는 필드 | 최초 구현은 빈 조각과 구분해 빈 키를 허용. 사용자의 a=1&=foo 질문에 해당 결과를 설명 | “key 없으면 400 bad request 보내자.” | 실제 필드는 키를 가져야 한다는 제약 추가. 명시적 빈 키를 사용하는 클라이언트는 거부. 빈 조각 무시 및 foo의 빈 값 허용과는 별개 |

사용자는 키 길이 검사의 이유도 확인했다. 구현은 form_decode 성공 후 key.length가 0인지 확인한다. 이는 실제 사용할 키를 검사한다는 구현 선택이며, 사용자에게 디코딩 후 검사가 필수라고 설명하지 않는다. 현재 디코더는 바이트를 없애지 않으므로 디코딩 전에도 빈 키를 판별할 수 있다.

빈 조각 검사는 필드 수 증가 전에 수행한다. 따라서 무시하는 조각은 100개 제한에 포함하지 않는다. &와 첫 =를 원문에서 먼저 찾고 각 키·값을 디코딩하므로 %26이나 %3D는 구분자로 다시 해석하지 않는다. 중복 키 거절은 유지한다.

| 입력 | 최종 결과 |
|---|---|
| HTTP 본문 길이 0 | 세 API 모두 400 invalid_body |
| a=1&foo | 200, {"a":"1","foo":""} |
| &a=1&& | 200, {"a":"1"} |
| && | 200, {} |
| a=1&=foo 또는 = | 400 invalid_body |
| key=%00 또는 원문 NUL을 포함한 키·값 | 400 invalid_body |

구현 기록: `67635f3` 빈 POST 본문 거부, `71f367f` 빈 업로드 타입·폼 NUL 거부, `b18a54f` 빈 세그먼트 무시, `3f500a2` 빈 키 거부. 각 작업에서 설계·함수 흐름·테스트 문서를 갱신했다. 첫 변경은 make test 전체 통과, 이후 변경은 JSON·POST 및 해당 작업의 HTTP 경계 테스트 범위에서 검증했다. 개별 결과는 F1 테스트 문서를 따른다.

#### 업로드 ID: atomic 제안에서 공유 카운터 없는 방향으로

| 순서·논점 | 제안·검토한 옵션 | 사용자 선택·질문 | 트레이드오프와 상태 |
|---|---|---|---|
| static unsigned long sequence의 안전성 | C11 atomic 순번 + PID + 기존 O_EXCL 재시도. 저장 전체를 mutex로 감싸는 방식은 불필요한 직렬화로 설명 | 멀티스레드에서 unique ID allocator도 병목이 되지 않는지 질문 | atomic은 메모리 데이터 레이스를 제거하지만 공유 카운터의 캐시 경합은 남음. 실제 병목 여부는 측정하지 않았으며 파일 I/O보다 크다고 단정하지 않음 |
| 공유 카운터 경합 회피 | PID + 스레드별 고유 번호 + 스레드 로컬 순번. 스레드 번호는 생성 시 한 번 부여 | 해당 조합을 인용하며 “이 공식으로 UUID 생성하기” 선택 | 요청마다 전역 카운터를 갱신하지 않음. 스레드 번호 발급·로컬 상태 관리가 필요하고 재시작·PID 재사용 시 과거 ID와 충돌할 수 있음 |
| 현업 UUID의 유일성 | UUID v4는 안전한 난수로 충돌 확률을 낮추며 중앙 순번 없이 발급. 저장 시 중복 방지와 재시도 병용 설명 | 유일성 보장 방식을 질문한 뒤 위 조합을 선택 | 선택한 조합은 표준 UUID가 아니라 커스텀 업로드 ID라고 정정. UUID v4를 채택한 것으로 기록하지 않음 |
| 파일 충돌의 최종 처리 | 기존 O_EXCL과 충돌 시 재시도 유지 제안 | 조합 기반 ID 설계 설명에 포함. 별도 신규 구현은 없음 | O_EXCL은 기존 파일 덮어쓰기를 막지만 C 공유 변수의 데이터 레이스를 해결하지 않음. 프로세스 워커는 각자 순번을 가져 충돌 가능성은 있어도 해당 변수의 스레드 데이터 레이스와는 다름 |

**ID 변경은 설계 방향만 선택했으며 아직 구현하지 않았다.** 현재 store_upload에는 static unsigned long sequence가 남아 있다. atomic 적용도 완료한 것으로 취급하지 않는다. 향후 스레드·워커 구조를 구현할 때 스레드 고유 번호의 발급·수명과 ID 형식을 구체화해야 한다.

업로드 저장 경로의 상대 경로 의존 및 디렉토리 자동 생성은 문제 맥락으로 제시됐지만, 이번 대화에서 새 정책으로 변경하지 않았다. filename 빈 문자열 거부도 에이전트가 제안했으나 사용자가 선택한 빈 content_type 검증에 묶어 구현하지 않았다.

## F2_multithread

이 세션에서 연결 단위 스레드 풀 초안을 검토한 뒤, 사용자가 epoll 수신부와 요청 단위 pthread 풀을 조합하는 방향을 제시했다. 아래는 실제 선택과 아직 선택하지 않은 추천안을 구분한 기록이다. 문서 작성 요청을 추천안 전체의 승인으로 해석하지 않는다.

상세 계획은 [F2 설계](F2_multithread/f2_design.md), [함수 흐름](F2_multithread/f2_funcflow.md), [검증 계획](F2_multithread/f2_testcases.md)을 참조한다. 현재 F2는 문서 단계이며 제품 구현·성능 검증을 완료하지 않았다.

### 1. 연결 단위 풀에서 요청 단위 풀로 방향을 바꿨다

| 순서·상황 | 에이전트가 제안한 옵션·설명 | 사용자 선택·확인 근거 | 이점과 감수한 점 |
|---|---|---|---|
| 1. 동시 요청을 처리하고 싶음 | 고정 워커 풀 + 공통 연결 큐. 워커가 handle_connection을 종료까지 실행 | “멀티 스레드를 사용하고싶어”, 설계·함수 흐름 초안 요청. 구체적인 연결 단위 풀은 당시 제안이며 최종 확정 아님 | 기존 HTTP 처리 함수를 재사용하기 쉬움. 느린 헤더·본문 수신과 keep-alive 대기 동안 워커가 점유됨 |
| 2. 논블로킹인데 동시 처리하지 못하는 이유 확인 | main → handle_connection → 수신/idle poll 호출 경로 설명 | 소켓 분리, poll 위치, 함수 흐름을 차례로 질문 | 논블로킹 recv/send와 연결 간 작업 전환이 별개임을 확인. 이 설명 요청 자체는 신규 구조의 승인 아님 |
| 3. 수신 대기를 워커에서 분리 | 앞단 이벤트 루프가 여러 연결을 수신·파싱하고 완성 요청을 공통 큐에 전달 | 사용자가 “앞단에 epoll”, “뒷단에 thread(worker) pool”, “request가 다 온것들만 작업 큐”를 제시하고 반영 계획 요청 | 느린 수신·idle 연결이 워커를 점유하지 않음. 연결별 버퍼·기한·상태, 작업 인계와 완료 회수, 동일 연결의 응답 순서 관리가 필요 |
| 4. 실행 플랫폼 | Linux 전용 epoll / macOS kqueue도 제공 | “도커에서 환경에서 실행할거임”에 따라 Linux 컨테이너 실행 방향으로 정리 | epoll·eventfd 중심으로 구현 가능하고 백엔드 이중 구현을 줄임. macOS 호스트에서 해당 서버 경로를 직접 실행할 수 없으며 Linux 컨테이너에서 빌드·통합 검증 필요 |

사용자가 말한 “request가 다 온 것”의 기존 코드상 판정은 POST는 본문까지, GET은 헤더까지다. GET 본문 전체를 기다리도록 정책을 바꾼 것으로 기록하지 않는다. epoll은 읽기 가능 이벤트를 제공하고, 요청 완료는 http_parse_request가 판단한다. 연결 수 제한도 epoll 자체의 기능이 아니라 별도 카운터·수락 정책으로 구현한다.

### 2. 사용자가 앞으로 결정할 정책과 트레이드오프

아래 추천은 세션에서 제안된 출발점이며 **아직 사용자 선택이 없다.** 각 수치는 측정으로 검증한 적정값이 아니다.

| 논점·상황 | 제안·검토한 옵션 | 사용자 선택·현재 상태 | 이점과 감수한 점 |
|---|---|---|---|
| 응답 전송 담당 | A: 워커가 처리·전송까지 수행(초기 추천). B: 워커는 준비만 하고 이벤트 루프가 EPOLLOUT으로 전송 | 미결정 | A는 http_respond/http_send_all을 재사용하여 변경 범위가 작음. 송신 poll 동안 워커가 점유되고, 조금씩 계속 읽는 상대에게는 전체 전송 시간이 길어질 수 있음. B는 느린 송신도 워커에서 분리하지만 응답 준비/송신 API 분리, 부분 전송 위치·파일 FD·응답 버퍼 수명 관리가 추가됨. 파일 읽기까지 루프에 두면 디스크 대기가 루프를 막을 수 있어 작업 경계도 필요 |
| 워커 수 N | 4개로 시작 제안. 적게/많게 설정 | 미결정 | 적으면 스택 메모리·스케줄링 비용이 작지만 처리·송신 대기에 따른 병렬 처리 한도가 낮음. 많으면 대기 중 다른 작업을 처리할 여지가 늘지만 CPU·메모리·파일 I/O 경합이 커질 수 있음. Docker CPU/메모리 제한과 부하를 보고 조정 |
| 작업 큐 Q | 대기 작업 16개로 시작 제안. 작은/큰 제한 큐 | 미결정 | 작은 큐는 대기 지연과 메모리를 제한하지만 짧은 요청 집중도 빨리 거절할 수 있음. 큰 큐는 일시적 집중을 흡수하지만 처리량 자체를 늘리지 않으며 지연·버퍼 보유 시간이 증가. 실행 중 워커 N개와 READY 대기는 Q와 별도로 계산 |
| 최대 연결 수 | 수락 후 미종료 연결 128개로 시작 제안 | 미결정 | 작은 상한은 FD·연결 메모리를 제한하지만 정상 idle 연결도 신규 접속을 막을 수 있음. 큰 상한은 더 많은 클라이언트를 유지하지만 부분 본문·idle 연결이 자원을 오래 보유. RECV/READY/QUEUED/WORKING/IDLE/DISCARD 모두 포함 |
| listen backlog | 128로 시작 제안 | 미결정 | 큰 값은 accept 전 연결 집중을 흡수하지만 애플리케이션 처리량이나 연결 상한을 늘리지 않음. 작은 값은 커널 대기가 적지만 집중 시 연결 실패·재시도가 늘 수 있음. 실제 적용 크기는 OS 설정에도 제한됨 |
| 전체 수신 버퍼 예산 | 32 MiB로 시작 제안. 연결별 기존 상한과 함께 제한 | 미결정 | 작은 예산은 메모리 고갈을 억제하지만 여러 정상 POST를 동시에 받기 어려워짐. 큰 예산은 큰 요청 동시 수신을 허용하지만 컨테이너 메모리 부담 증가. 실제 할당 capacity 합계를 제한하는 등 계측 기준이 필요하며 송신·JSON·스레드 메모리는 별도 |
| 연결 상한 도달 | A: listener 감시 일시 중지 후 공간 확보 시 재개(추천). B: 추가 accept 후 즉시 close | 미결정 | A는 애플리케이션 연결 수를 유지하며 커널 대기열로 넘기지만 접속 지연이 늘고 backlog 포화 시 실패 가능. B는 연결을 빨리 거절하지만 accept/close 비용과 클라이언트 재시도 부하가 발생 |
| 작업 큐 포화 | A: READY에서 제한 대기(추천). B: close. C: 503 응답 | 미결정. 추천 대기값은 5초 | A는 순간적인 집중을 흡수하지만 큐 밖의 READY도 메모리·연결 슬롯을 차지하므로 개수/기한 제한 필요. B는 가장 단순하고 자원 회수가 빠르지만 HTTP 오류 설명 없이 끊김. C는 과부하를 알릴 수 있지만 작업 큐가 찬 상태에서도 제한된 오류 송신 경로가 필요하며 main에서 대기 송신하면 안 됨 |
| 큐 대기 기한 | READY 최대 5초 후 close 제안. QUEUED 포함 여부와 기한 기준은 추가 정의 필요 | 미결정 | 짧으면 처리 시작 전 자원을 빨리 회수하지만 정상 순간 부하도 거절. 길면 처리 기회가 늘지만 오래된 요청과 메모리 보유가 증가. 5초를 요청 전체 응답 시간 보장으로 해석하지 않음. 이미 워커에 전달한 작업의 취소에는 별도 동기화 필요 |
| 수신 버퍼 예산 초과 | 해당 연결 close 제안. 대안으로 수신 일시 중지 후 공간 확보 시 재개 | 미결정 | close는 예산을 지키기 단순하지만 정상 요청도 중단될 수 있음. 수신 중지는 요청을 보존하지만 별도 대기 상태·재개 순서·기한 관리가 필요하고 기존 버퍼는 계속 메모리를 차지 |
| 종료 시 작업 처리 | A: 신규 접수 중단 후 큐에 든 작업·실행 중 작업 완료(추천). B: 대기 작업 폐기, 실행 중 작업만 완료. C: 즉시 종료 | 미결정. READY/부분 수신 연결 처리와 전체 종료 기한도 필요 | A는 접수한 작업 손실을 줄이지만 큐와 느린 응답 때문에 종료가 길어짐. B는 종료 시간을 줄이나 대기 요청을 잃음. C는 가장 빠르지만 응답·업로드 파일쌍이 중간 상태로 남을 수 있음. 어떤 방식이든 실행 중 객체를 먼저 해제하지 않도록 수명 관리 필요 |
| 전체 종료 기한 | 완료까지 무기한 대기 / 기한 후 중단 | 미결정, 추천 수치 없음 | 무기한은 진행 중 작업을 보존하지만 종료가 끝나지 않을 수 있음. 기한은 운영 시간을 제한하지만 요청·저장이 중단될 수 있음. 기존 쓰기 제한은 진행 없는 5초이므로 전체 작업의 5초 완료를 보장하지 않음. 스레드 강제 취소는 잠금·파일 정리를 복잡하게 하므로 중단 방식을 따로 설계 |
| 설정 전달 방식 | 코드 상수(초기 추천) / CLI / 설정 파일 | 미결정 | 상수는 구현·학습이 단순하지만 조정마다 재빌드. CLI는 Docker 실행별 조정이 쉽지만 범위·조합 검증과 실행 옵션 관리가 필요. 설정 파일은 항목이 많을 때 편하지만 파싱·배포·기본값 정책이 추가됨 |
| 업로드 ID 구체화 | 기존 선택인 PID + 워커 번호 + 스레드 로컬 순번 유지, O_EXCL 충돌 재시도 제안 | 조합 방향은 F1에서 선택. 최종 형식·순번 소진·비워커 호출 문맥은 미결정 | 요청마다 공유 카운터 갱신을 피하지만 재시작·PID 재사용 때 과거 ID와 충돌 가능. O_EXCL은 덮어쓰기를 막지만 다수 기존 ID와 충돌하면 재시도 비용·기존 재시도 상한에 따른 실패가 생길 수 있음. 워커 번호 부여·수명과 테스트용 상태 초기화가 필요 |

초기 추천값은 N=4, Q=16, MAX_CONNECTIONS=128, backlog=128, 수신 버퍼 예산=32 MiB다. CPU 처리 병렬성·대기 작업 수·열린 연결 수·커널 대기열·메모리 한도를 각각 제어하는 값이며 하나의 동시 요청 수로 합쳐 해석하지 않는다.

### 3. 구현 기법 제안과 사용자 정책을 구분한다

LT 방식 epoll, 인계 중 감시 해제, generation으로 오래된 이벤트 구분, mutex/condition variable 작업 큐, 완료 큐+eventfd, 동일 연결당 실행 작업 한 개는 현재 설계의 구현 제안이다. 사용자에게 개별 승인받은 구현으로 기록하지 않는다.

- condition variable 알림은 워커를 깨우고, 상태변수는 처리 가능 여부를 판단한다. 상태변수만 변경하는 것은 알림을 대체하지 않는다.
- 이벤트 루프는 수신/idle 대기를 관리하고, 워커 인계 중에는 버퍼·FD를 동시에 변경하지 않는다. 최종 close와 객체 해제는 완료 회수 뒤 진행하는 안이다.
- 기존 GET 본문 폐기·POST 수신·keep-alive·응답 순서는 유지 대상으로 잡았다. 사용자가 새 구조를 제시한 것을 기존 HTTP 정책 변경으로 해석하지 않는다.

설계 기록: `c8c5593` 연결 단위 풀 초안, `ff996b3` epoll + 요청 단위 풀 전환 계획. 이후 Docker 실행 방향이 결정됐으며 이 기록에 반영했다. F2의 구현 완료 또는 성능 개선 실측 결과는 아직 없다.

### 4. 자원·송신·과부하 정책을 확정했다

앞 절의 미결정 표는 당시의 제안 이력이다. 이후 사용자가 아래 정책을 선택했으며 현재 F2 계획에는 이 절을 우선 적용한다. 선택 완료와 제품 구현 완료는 구분한다.

| 논점·상황 | 제안·검토한 옵션 | 사용자 선택·확인 근거 | 이점과 감수한 점 |
|---|---|---|---|
| 응답 전송 담당 | 워커가 준비·송신 / 워커는 준비만, main이 EPOLLOUT 송신 | “워커는 응답 준비만, main이 EPOLLOUT으로 전송” | 느린 송신자가 워커를 점유하지 않음. 기존 http_respond를 준비/부분송신으로 분리하고 응답 자원·전송 위치·파일 청크 읽기 경계를 관리해야 함 |
| 자원 상한 | 초기 추천 워커4/큐16/연결128/수신32 MiB | “워커수 4개, 작업큐 크기 64 최대 연결수 128, 전체 수신 버퍼 한도 32Mib” | 큐를 64개로 늘려 순간 집중을 더 흡수하지만 처리량 자체가 늘지는 않고 대기 지연·버퍼 보유가 증가. 수신 버퍼 외의 응답·스레드 메모리는 별도. backlog=128은 선택한 값에 포함되지 않음 |
| 연결 상한 | accept 일시 중지 / accept 후 503 | 처음 “accept 일시 중지 및 에러 반환”을 제시. 두 동작을 동시에 적용하기 어렵다는 설명 뒤 “accept 일시 중지”로 확정 | 추가 애플리케이션 연결을 만들지 않음. 수락 전 연결에 HTTP 오류는 반환하지 않으며 커널 대기·접속 지연·backlog 포화가 가능. 슬롯 확보 후 수락 재개 |
| 작업 큐 포화 | READY 제한 대기 / 503 후 close / 즉시 close | 완료 요청을 큐에 못 넣는 상황인지 확인한 뒤 “오케이 503 전송후 close 로 결정” | 과부하를 HTTP로 알리고 큐 밖 대기열을 늘리지 않음. 포화된 작업 큐와 독립된 고정 오류 응답을 main이 준비·EPOLLOUT 전송해야 함. 전송 실패·상대 종료·기한 초과 시 전체 전달은 보장하지 못하며 정리 필요 |
| 수신 버퍼 예산 초과 | 연결 close / 수신 중지·재개 | “버퍼 예산 초과 연결 -> close” | 자원 회수를 단순화하지만 정상 요청도 중간 종료 가능. 실제 capacity 합계 등 예산 계측 기준은 추가 정의 필요 |
| 서버 종료 | 큐·실행 작업 완료 / 대기 작업 폐기 / 즉시 종료 | “이미 큐에 들어간 작업 + 실행중인 작업”까지 완료 후 종료 | 접수한 작업의 손실을 줄임. 선택한 송신 구조에 따라 main은 해당 응답 전송까지 유지되어야 함. 느린 송신·파일 작업으로 종료가 길어질 수 있고 전체 종료 기한·기존 SENDING/부분 수신 연결 처리는 미결정 |
| 설정 방법 | 코드 상수 / CLI / 설정 파일 | “CLI 인자로” | Docker 실행마다 재빌드 없이 조정 가능. 옵션명·기본값·단위·유효 범위 검증과 사용법 제공 필요 |

현재 상한 기본값은 워커4/대기 작업큐64/미종료 연결128/전체 수신 버퍼32 MiB로 계획한다. 큐 포화 시 main이 만드는 503 응답은 기존 큐의 작업을 취소하거나 워커 처리를 기다리지 않는다. 503에는 Connection: close를 지정하고 전송 완료 뒤 닫으며, 송신 실패 시에도 정리한다.

남은 정책은 backlog, CLI 세부 규약, 버퍼 계측 기준, 파일 청크 공급 경계, 전체 종료 기한과 종료 시 연결별 처리, 이미 큐에 들어간 요청의 대기 기한, 업로드 ID 세부 형식이다. 이번 결정으로 이전 READY 5초 대기 추천이나 워커 송신 추천이 채택된 것으로 취급하지 않는다.

### 5. CLI·메모리 계측·종료·ID의 세부 정책을 좁혔다

| 논점·상황 | 제안·검토한 옵션 | 사용자 선택·확인 근거 | 이점과 감수한 점 |
|---|---|---|---|
| CLI 이름·backlog 노출 | 긴 플래그와 --backlog / 짧은 이름 | “--worker 4 --queue 64 --max 128 --buffer 32”. backlog는 굳이 노출하지 않는 방향 | 입력이 간결해짐. --buffer 단위는 MiB로 문서화 필요. 내부 listen backlog 값 자체는 아직 확정하지 않음 |
| 수신 메모리 계측 | 실제 데이터 length / 할당 capacity 합계 | “모든 연결의 할당된 capacity 합계” | 실제 확보한 버퍼를 제한. 여유 공간도 예산에 포함되며 realloc 실패·해제 시 정확한 회계 필요 |
| 파일 청크 크기 | 워커에서 8 KiB씩 읽고 main이 송신하는 안 | “왜 8Kib인지 설명하기”로 질문, 크기/방식 승인 아님 | 작은 청크는 메모리가 적으나 큰 파일에서 큐·완료 알림·읽기 호출 증가. 8 KiB는 필수값이나 측정된 최적값이 아니며 기존 GET 16 KiB 유지도 가능 |
| 종료 상세 | 부분 수신·idle close, 큐/실행/송신 중 응답 완료 후 close, 전체 종료 기한 없음 | “종료 처리: 제안대로 하기” | 접수 작업과 전송 중 응답을 보존. 조금씩 진전되는 전송·긴 파일 작업으로 종료가 길어질 수 있음. 송신 진행 없음 5초 제한은 유지 |
| 큐 대기 timeout | 별도 기한 없음 제안, Nginx와 비교 | “nginx에서는 어떻게 하는지?”로 질문. 정책 채택은 아직 없음 | Nginx 공식 thread_pool에는 별도 큐 timeout 설정이 없고 max_queue 포화 시 오류. 우리 큐에 별도 기한을 둘지는 다음 결정으로 남김 |
| 업로드 ID 순번 | PID_워커번호_로컬순번, uint64_t 소진 시 실패 | 조합과 실패 정책을 제시하고 “넘칠수가 있는지?” 질문 | 실제 소진 가능성은 매우 낮지만 숫자 범위는 유한. wrap 방지·소진 상태를 명시하고 테스트는 경계값 주입. 재시작의 기존 파일 충돌은 별도 O_EXCL 재시도 문제 |

Nginx 비교 근거: [공식 thread_pool 문서](https://nginx.org/en/docs/ngx_core_module.html#thread_pool). upstream 서버 선택용 queue timeout은 별도 기능이며 파일 I/O 스레드 풀의 대기 기한으로 혼동하지 않는다. 이번 정책 반영도 문서 작업이며 F2 실행 검증 결과를 의미하지 않는다.


### 6. 파일 청크와 큐 대기 정책을 확정했다

| 논점·상황 | 제안·검토한 옵션 | 사용자 선택·확인 근거 | 이점과 감수한 점 |
|---|---|---|---|
| 파일 청크 | 8 KiB 초기 제안 / 기존 16 KiB 유지 추천 | “파일 청크 16 KiB 유지, 큐 대기 기한 없음으로 확정할까요?”에 “ㅇㅇ 확정하기” | 기존 크기를 유지하고 8 KiB 대비 읽기·큐 왕복을 줄일 수 있음. 연결당 하나를 유지하면 128개 연결 청크 메모리는 최대 2 MiB로 수신 버퍼 예산과 별도. 측정된 최적값이라는 뜻은 아님 |
| 큐 대기 기한 | 별도 제한 없음 / 기한 후 취소 | 같은 묶음 제안에 동의 | 큐 취소·만료 관리가 단순해지고 기존 작업을 보존. 워커가 오래 걸리면 대기도 길어짐. 큐64 제한·포화 시503과 기존 수신/idle/송신 기한은 유지 |

이 결정은 청크 크기와 큐 대기 기한을 확정한 것이며, 파일 후속 읽기 작업이 큐 포화 시 재제출되는 세부 정책까지 승인한 것으로 넓혀 해석하지 않는다. 제품 구현과 실행 검증은 아직 수행하지 않았다.

### 7. F2 구현과 검증으로 연결했다

| 논점·상황 | 구현 선택 | 사용자 선택·확인 근거 | 이점과 감수한 점 |
|---|---|---|---|
| 파일 후속 읽기가 큐 포화에 걸림 | READ_PENDING에서 감시를 해제하고 작업 슬롯 확보 후 재제출 | 서브에이전트 구현 전 후속 읽기의 재제출 방식에 동의 | 이미 시작한 파일 응답에503을 끼워 넣지 않으며 main을 막지 않음. 큐 대기 동안 파일 응답 완료가 늦어질 수 있음 |
| CLI 세부 범위·backlog·테스트 ID | 양수 범위 검사, 내부 backlog128, 비워커 TLS 번호는2^32 이상 | 확정한 정책을 구현하는 세부 기준으로 문서화. 별도 사용자 정책 선택으로 꾸미지 않음 | 기본 제한과 번호 분리를 구체화. 지정한 상한 범위 내라도 실제 메모리·스레드 할당이 실패하면 시작 취소 |
| 기존 호출자 보존 | http_respond는 준비 API+기존 송신의 호환 경로로 유지, 실제main은 epoll 부분송신 사용 | 기존 HTTP 계약 유지·작은 단위 구현 요청에 따라 적용 | 기존 테스트/호출자가 유지됨. 호환 poll 경로와 제품 epoll 경로를 각각 검증해야 함 |
| 업로드 디렉토리 | Docker 빌드 시 uploads_storage 준비, 서버는 자동 생성하지 않음 | 기존 F1 저장소 존재 계약 유지 | 기본 이미지에서도 업로드 가능. 컨테이너 삭제 시 데이터는 소실되므로 지속하려면 마운트 필요 |

구현 브레이크포인트: `24ba267` 응답 준비 API·TLS 업로드 ID, `e7f790e` bounded pthread 풀, `173bec2` epoll 실제 서버·CLI·Docker 통합. Docker 실제main 검증과 HTTP 전체 회귀, 비root 권한 테스트를 통과했다. ASan/LSan/UBSan 전체 회귀와 검증용 seccomp=unconfined 컨테이너의 TSan 풀/ID/실제main 검증도 통과했다. 처리량 개선을 실측한 결과는 아니며 구체적인 실행 방법과 제한은 F2 테스트 문서에 기록한다.
