# wrk 기능·부하 테스트 계획

작성일: 2026-11-25. 상태: **계획·실행 도구 작성 및 핵심 축약 검증 진행**. 원래 전체 매트릭스와 최장 16분 유지는 미실행이며, 실제 범위는 하단 실행 기록을 따른다.

## 1. 목적과 확정 범위

동시 다중 클라이언트가 접속했을 때 epoll 이벤트 루프가 요청을 진행시키는지 확인하고, 동시성과 유지 시간에 따른 처리량·지연·오류·자원 사용을 측정한다.

사용자가 확정한 사항:

- 기능 테스트의 주 도구는 wrk다.
- 부하 테스트의 동시 요청과 일정 시간 유지(tolerance) 모두 wrk를 사용한다.
- 입력은 선형이 아닌 지수 증가 방식으로 올린다.

이 문서의 동시성은 wrk `-c`의 **유지하려는 연결 수**다. 단위 시간당 요청 수(RPS) 입력과 같지 않다. 기본 요청 흐름은 연결별 응답을 받은 뒤 다음 요청을 보내며, 동시 연결 증가가 실제 요청 도착률의 배증을 보장하지 않는다. 파이프라이닝은 사용하지 않는다.

이하 시간·파일 크기·반복 횟수·중단 기준은 재현 가능한 첫 실행을 위한 **제안값**이다. 아직 사용자 확정 성능 목표나 실행 결과가 아니다. 제품 정책 변경이 필요하면 구현 전에 합의한다. hey·ApacheBench는 이번 실행 범위에서 제외한다.

## 2. 현재 코드 기준

```text
wrk HTTP/1.1 요청
  → main: CLI 설정, event_loop_run
  → epoll: accept / 수신 / http_parse_request
  → 제한 작업 큐 → pthread 워커: 응답 준비·파일 읽기
  → 완료 큐 / eventfd → epoll EPOLLOUT: 부분 송신
  → 다음 요청 또는 연결 정리
```

- 서버는 Linux epoll을 사용한다. 실제 제품 main을 Linux Docker에서 실행한다.
- 기본값: `--worker 4 --queue 64 --max 128 --buffer 32`(MiB).
- 포트는 현재 8000 고정, 정적 루트는 실행 디렉토리의 `www`다.
- 최대 연결에는 수신·큐 대기·처리·송신·idle 상태가 포함된다. 상한 도달 시 listener 감시를 중단하고 공간이 생기면 재개한다.
- 작업 큐 포화 시 신규 완료 요청에 503과 Connection: close를 반환한다. 연결 상한 도달과 큐 포화는 다른 상황이다.
- keep-alive idle 5초, 연결당 최대 100요청. 부하 중 주기적인 연결 재생성은 정상 동작이다.
- 헤더 5초·POST 본문 10초는 전체 수신 기한, 송신은 마지막 양수 send 이후 무진전 5초다.

참조: [F2 설계](F2_multithread/f2_design.md), [기존 F2 검증](F2_multithread/f2_testcases.md).

## 3. 환경과 사전 준비

1. 실행 직전 Git HEAD와 `git diff`를 보관한다. 미커밋 소스가 있으면 측정 대상에 포함되는지 명시하고, 해시만으로 재현 가능하다고 표현하지 않는다. 사용자 변경을 자동 정리하지 않는다.
2. Linux 커널·아키텍처, CPU·메모리, Docker CPU/메모리 제한, 컴파일러·CFLAGS, wrk 버전, FD 제한, 서버 옵션, 부하 발생기 위치를 기록한다.
3. 제품 빌드와 기능 회귀(`make test`, `make test-f2`)를 통과시킨다. 성능 측정에는 sanitizer를 사용하지 않고 기본 `-O2` 빌드를 쓴다.
4. 호스트 글로벌 설치 대신 tests/perf/Dockerfile의 전용 Ubuntu 이미지에 wrk를 준비했다. environment.sh build/up/exec/down으로 실행하며 실제 버전은 실행 환경 로그에 기록한다. hey는 이번 범위에 포함하지 않는다.
5. 서버·wrk·관측기는 전용 환경에서 실행하고 다른 부하를 중지한다. 서버와 wrk를 별도 컨테이너로 나누되 같은 Docker 네트워크에서 접속해 포트 포워딩 영향을 줄인다. 같은 호스트의 CPU·메모리는 여전히 공유한다.
6. 실제 제품 main이 사용하는 전용 테스트 저장소에만 fixture를 만든다. 기존 사용자 www·uploads_storage·8000 포트 서버는 사용하지 않는다.
7. 고정 fixture: `/perf/small.bin` 1KiB(주 측정), `/perf/medium.bin` 64KiB(전송량 비교), `/perf/large.bin` 16MiB(느린 수신 보조 검증). 내용과 SHA-256을 기록하고 측정 전 읽어 페이지 캐시를 준비한다. 디스크 cold-cache 성능은 이번 범위가 아니다.
8. 각 실행 전 서버를 시작하고 별도 5초 워밍업을 한다. 시작/종료 시각과 서버 PID를 기록한다. 측정 사이 10초 이상 쉬고 CPU·연결·FD가 안정됐는지 확인한다. 연결 생성형 실행은 TIME_WAIT·클라이언트 임시 포트도 확인한다.

주 성능 표에서는 작은 정적 GET을 고정한다. 64KiB·Connection: close는 별도 표로 분리하며 POST·업로드 처리량은 후속 범위다. 서버 설정을 단계마다 바꾸지 않는다.

## 4. 기능 테스트 — wrk 중심

wrk의 정상 응답은 이벤트 루프 내부의 공정성이나 모든 상태 전이를 단독 증명하지 못한다. 주 요청은 wrk로 만들고, 느린 헤더·idle·읽지 않는 연결은 작은 Python 보조 클라이언트 또는 기존 `tests/tools/test_epoll_server.py` 방식으로 제어한다. 결정적인 큐 포화는 기존 테스트 장벽을 재사용하며 성능 측정에 장벽을 넣지 않는다.

기능용 Lua `response(status, headers, body)`에서 기대 상태·본문·Content-Length를 확인하고 스레드별 검사 수·오류 수를 `done`에서 합산한다. 잘못된 응답을 출력만 하고 성공으로 처리하지 않도록 실행 래퍼가 최종 판정을 수행한다. 이 Lua/래퍼는 tests/perf 아래에 구현했다. 실제 실행 범위와 제약은 하단 및 전용 결과 문서를 따른다.

| ID | 시나리오·입력 | 큰 흐름과 기대 결과 |
|---|---|---|
| F01 | 정상 GET, C=1/2/4/8/16/32/64, 각 10초 | 동시 연결에서 200·고정 본문·길이 일치. 연결별 응답 혼입 없음 |
| F02 | URI에 클라이언트별 식별자를 넣은 작은 fixture 다수 | wrk 스레드별 미리 만든 요청/기대 본문으로 응답 대응을 확인. 스레드별 식별은 물리적 연결 식별과 다름을 기록 |
| F03 | 분할 헤더 8개 + 별도 wrk C=16 | 느린 헤더가 5초 기한을 기다리는 동안 정상 요청 완료 수가 증가. 보조 정상 요청이 느린 연결 만료 전 응답받는지 시각 기록 |
| F04 | idle keep-alive 8개 + wrk C=16 | 워커 수 4보다 많은 idle 연결이 있어도 정상 요청 진행. idle은 기존 5초 정책에 따라 정리 |
| F05 | 큰 파일을 읽지 않는 상대 1개 + wrk C=16 작은 GET | 큰 응답 전송이 멈춰도 작은 GET이 먼저 완료. 무진전 송신 연결 정리 후 정상 요청 계속 진행 |
| F06 | 작은 연결 상한의 전용 서버 + 상한을 채운 연결 | 추가 연결의 TCP connect 성공을 HTTP 처리 성공으로 해석하지 않음. 하나 해제 후 대기 요청 처리 재개; 상한 때문에 무조건 503을 기대하지 않음 |
| F07 | 워커·큐를 장벽으로 고정 포화 + 추가 wrk 요청 | 큐 포화 요청에 503/close, 장벽 해제 후 기존 작업과 새 정상 요청 진행. 포화 중 503은 의도한 결과이며 정상 성공과 따로 집계 |
| F08 | 부하 중 일부 보조 연결 종료, 이후 wrk 정상 요청 | 서버 크래시·교착 없이 다른 요청 계속 처리, 종료 연결 FD·버퍼 회수 |
| F09 | keep-alive로 연결당 100요청을 넘는 반복 트래픽 | 서버의 100요청 후 close를 wrk가 새 연결로 이어 처리. 같은 연결 재사용/정확한 종료 경계는 기존 명시적 소켓 테스트로 보완 |

F06/F07은 기본 설정 성능 실행과 분리한다. 정확한 연결 상태·큐 포화 판정은 보조 클라이언트와 기존 테스트 계측을 사용하며, wrk의 RPS만 보고 기능 통과라고 결론 내리지 않는다.

정상 기능 사례의 판정은 검증된 응답 1개 이상·상태/본문/길이 불일치 0·예상하지 않은 HTTP/소켓 오류 0·서버 생존이다. 느린 연결/의도적 종료/포화의 예상 오류는 원인별로 분리한다. 모든 클라이언트별 완료와 회수는 보조 기록으로 확인한다. 절대 지연 SLO는 아직 정하지 않는다.

## 5. 부하 A — 동시성 지수 증가

입력: `C(k)=2^k`, k=0..10.

```text
1 → 2 → 4 → 8 → 16 → 32 → 64 → 128 → 256 → 512 → 1024 연결
```

- 각 단계: 워밍업 5초 → 본 측정 30초 × 3회 → 실행 사이 회복 확인.
- `--latency --timeout 15s`, keep-alive 기본 사용, URI·fixture·서버 설정 고정.
- 최초 측정은 wrk 스레드 `-t1`을 모든 단계에 고정해 동시성만 바꾼다. 부하 발생기 CPU가 포화하면 결과를 서버 한계로 확정하지 않고 같은 매트릭스를 고정 `-t2` 또는 별도 발생기에서 다시 수행한다. C=1은 스레드 수가 연결 수를 넘지 않도록 별도 기준선으로 둔다.
- 1..128: 설정된 연결 상한 이내 구간. 큐가 먼저 포화될 수 있으므로 모든 단계를 무오류라고 사전 가정하지 않는다.
- 256..1024: 연결 상한·backlog를 넘는 과부하 탐색. 대기·연결 오류·timeout·503과 복구를 기록하며 정상 처리량 목표 구간과 구분한다. 클라이언트 C는 서버의 실제 수락 연결 수가 아니다.
- 1KiB 매트릭스를 먼저 완료한 뒤 64KiB를 같은 조건으로 별도 실행한다.
- Connection: close 매트릭스는 `-H 'Connection: close'`로 별도 실행한다. 기본 keep-alive 결과와 합치지 않는다.

wrk는 응답을 기다리며 다음 요청을 보내는 closed-loop 도구다. 지연 증가 시 실제 도착률도 달라지며, 이 결과로 고정 RPS에서의 SLO나 과부하 대기 전체를 입증하지 않는다.

### 측정 항목과 요약

- wrk 원본 로그: 완료 요청 수·전체 RPS·전송량·socket connect/read/write/timeout 오류·비정상 상태 수.
- 지연: 평균·p50·p95·p99·최대. 기본 `--latency` 출력에 없는 p95는 최소한의 Lua `done`에서 `latency:percentile(95.0)`으로 출력한다. 시간 단위(µs→ms)를 명시한다.
- 서버/발생기 각각 CPU·RSS·FD·스레드 수·네트워크 송수신, 서버의 수락 연결 수는 관측 가능하면 별도 계측.
- 기본 wrk RPS에 503 등 오류 응답도 포함될 수 있다. **전체 응답 RPS와 200 성공 RPS를 구분**한다.
- 순수 처리량 실행은 `response` 콜백을 끄고 최소 `done`만 사용한다. 같은 조건의 별도 진단 실행에서 Lua 상태별 집계로 200/503/기타를 확인한다. 진단 실행의 성공 RPS는 해당 실행의 200 수/시간으로 계산하며 순수 실행의 수치와 혼합하지 않는다. wrk 기본 status 오류는 >399 집계이므로 예상치 않은 3xx도 진단에서 별도 확인한다.
- 3회 RPS의 중앙값과 범위, 각 실행의 지연·오류를 나란히 보관한다. p99를 요청 원본 없이 합산한 통합 백분위로 표현하지 않는다.

성능 수치의 절대 합격선은 첫 측정 전 미정이다. RPS가 더 늘지 않으면서 지연·오류가 증가하는 지점을 포화 후보로 기록하고, 발생기/네트워크/컨테이너 제한인지 확인한다. RPS 자체를 목표치로 임의 확정하지 않는다.

## 6. 부하 B — 일정 시간 유지(tolerance)

여기서 tolerance는 정해진 부하를 지속할 때 서비스와 자원이 안정적인지 확인하는 유지 테스트를 뜻한다. 허용 오류율이나 시간 SLO가 이미 정해졌다는 뜻은 아니다.

1. 부하 A에서 예상하지 않은 오류가 없는 가장 높은 동시성 단계를 C_safe로 선택한다. 서버 설정 상한 이하로 제한한다. 무오류 단계가 없으면 먼저 원인을 조사하고 유지 테스트를 시작하지 않는다.
2. C_safe를 고정하고 실행 시간을 `D(k)=30×2^k초`, k=0..5로 늘린다.

```text
30초 → 60초 → 120초 → 240초 → 480초 → 960초
```

3. 각 시간 단계는 독립 실행이며 동일 조건으로 서버 재시작·워밍업 후 진행한다. 전체 구간의 메모리 누적은 최장 960초 단일 실행 안에서 관찰한다. 단계 사이 재시작이 누수를 해결했다고 해석하지 않는다.
4. 시간 단계는 우선 각 1회 수행하고 이상 단계만 동일 조건으로 재현한다. 동시성과 시간을 동시에 올리지 않는다.
5. 1초마다 CPU·RSS·FD를 수집한다. 시작/중간/끝의 별도 정상 probe 완료·지연도 기록하고, probe 요청은 wrk 트래픽과 구분한다.
6. 종료 후 신규 유휴/수신 기한이 만료될 시간을 두고 연결·FD·RSS 회복과 새 GET 성공을 확인한다. RSS는 할당자 캐시 때문에 정확히 초기값으로 복귀한다고 요구하지 않는다. FD·활성 연결은 측정 환경의 기준선과 비교한다.

유지 기능의 최소 판정은 서버 생존·정상 probe 계속 완료·예상하지 않은 응답/소켓 오류 0이다. RSS 증가율·지연 악화·처리량 하락은 관찰 지표로 기록하고, 수치 허용선은 첫 기준선 측정 후 합의한다. 16분 통과를 수시간/수일 안정성 보장으로 표현하지 않는다.

## 7. 중단·복구와 측정 혼선 방지

- 제안 중단 기준: 서버 크래시/교착, 정상 probe 3회 연속 15초 timeout, 지속 증가하는 FD/RSS로 자원 고갈이 예상되는 경우. 실패 로그와 자원 표본을 보존하고 더 높은 단계로 진행하지 않는다.
- 높은 동시성에서 503이나 연결 오류가 생긴 사실만으로 즉시 서버 버그라고 판단하지 않는다. 해당 단계를 과부하로 기록하고 부하를 내려 회복 여부를 먼저 확인한다.
- 클라이언트 임시 포트·FD·CPU 고갈, listen backlog, Docker CPU throttling·메모리 제한은 서버 이벤트 루프 한계와 분리한다.
- 성능 측정과 sanitizer·다른 테스트·병렬 벤치마크는 동시에 실행하지 않는다. 본문 검증 Lua와 상세 로그도 측정 오버헤드로 기록한다.
- 처리량 측정에서 사용자 데이터 변경·업로드 저장 누적·전역 커널 설정 변경은 하지 않는다. 필요한 변경은 별도 합의한다.

## 8. 실행 예시와 산출물

아래 명령은 Linux의 준비된 전용 실행 환경에서 사용하는 예시다. `${PERF_BASE_URL}`은 실제 테스트 서버 주소로 지정한다. 환경·래퍼·Lua·관측기는 tests/perf에 구현했으며 구체적인 명령은 tests/perf/README.md를 따른다.

```bash
# 전용 fixture/디렉토리를 준비한 제품 서버
./webserver --worker 4 --queue 64 --max 128 --buffer 32

# 기능 진단: EXPECTED_FILE 인자로 본문 fixture 지정
wrk -t1 -c16 -d10s --timeout 15s -s tests/perf/validate.lua \
  "${PERF_BASE_URL}/perf/small.bin" -- /fixtures/www/perf/small.bin

# 기본 처리량: percentiles.lua는 response 콜백 없음
wrk -t1 -c64 -d30s --timeout 15s --latency -s tests/perf/percentiles.lua \
  "${PERF_BASE_URL}/perf/small.bin"

# 연결 생성형: 별도 매트릭스로 기록
wrk -t1 -c64 -d30s --timeout 15s --latency -H 'Connection: close' \
  "${PERF_BASE_URL}/perf/small.bin"

# 유지 시간 예시: C_safe=32인 경우
wrk -t1 -c32 -d960s --timeout 15s --latency \
  "${PERF_BASE_URL}/perf/small.bin"
```

구현 도구/기록 대상:

- `tests/perf/validate.lua`, `percentiles.lua`, 상태별 진단 Lua와 실행 래퍼·보조 클라이언트·자원 관측기.
- `build/perf-results/<실행ID>/`: 환경·소스 상태·fixture 해시·명령·원본 wrk/서버 로그·자원 CSV·판정.
- 결과 표: 시나리오 / 파일 크기 / keep-alive 여부 / C / wrk 스레드 / 시간 / 반복 / 전체·성공 RPS / p50·p95·p99 / HTTP 상태 / socket 오류 / CPU·RSS·FD / 회복 결과.
- 실제 실행 후 본 문서 또는 별도 결과 문서에 실행일·커밋·변경 상태·통과/실패/미실행과 한계를 기록한다. 아래 핵심 검증 기록 외의 전체 계획은 미실행이다.

## 9. 미결정 사항

- 절대 목표: 성공 RPS, p95/p99 상한, 허용 오류율, RSS 증가율. 첫 기준선 결과를 보고 합의한다.
- 제안한 단계·시간·중단 기준과 별도 물리 부하 발생기 필요 여부는 실행 전 확인한다.
- 서버 worker/queue/max 튜닝 비교·POST/업로드·고정 요청 도착률 테스트는 이번 범위 밖이며 필요 시 별도 계획한다.

## 10. 구현 및 핵심 축약 실행 기록

사용자에게 핵심/전체 범위를 질문했으며 아직 응답이 없어, 핵심 축약 범위를 가정해 도구와 실행 경로를 검증한다. 전체 부하 계획의 완료나 성능 합격을 의미하지 않는다.

- [실행 도구 사용법](../tests/perf/README.md)
- [환경 검증](perf_environment_results.md): 전용 Docker 서버/발생기, 실제 HTTP/1.1·200 본문·PID 관측·정상 종료.
- [기능 검증](perf_functional_results.md): F01 동시성 1..64 각 1초, F02/03/04/05/08 각 1초, F09 명시적 100요청 종료와 wrk 10초 재연결. 총 검증 응답 5,155개에서 불일치·예상하지 않은 소켓 오류 0. F06/F07는 기존 실제-main 소켓/장벽 통합 검사로 보완했다.
- [부하 실행기 검증](perf_runner_results.md): 기본 dry-run, 명시적 execute, pure/diagnostic 분리, Linux 서버·발생기 자원 관측. 동시성 1..1024의 1초×1회 및 유지 1/2/4/8초의 실제 완료 결과는 해당 문서에 기록한다.

기능 보완 범위: F05는 느린 송신 중 다른 요청의 진행을 검사하며 정확한 송신 timeout 자체는 이번 runner에서 재검증하지 않는다. F08은 끊김 후 진행/복구를 확인하며 해당 사례별 FD 회수는 직접 계측하지 않았다. F02는 물리 연결별 식별이 아닌 wrk 스레드별 식별이다. 상세 제약은 전용 결과 문서를 따른다.

미실행: 전체 파일크기·연결모드 매트릭스의 30초×3회 측정, 30~960초 유지, 수치 SLO 판정. 제품 코드와 기존 사용자 변경은 보존한다.
