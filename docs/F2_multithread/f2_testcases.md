# F2. 검증 계획

## 이번 초안의 실제 확인 결과

- main.c: handle_connection 반환 전 다음 accept를 호출하지 않는 직렬 흐름 확인.
- http_connection.c/.h: 연결 전용 버퍼, 유휴 5초, 최대 100개 요청, 호출자 close 계약 확인.
- http_post.c: store_upload의 static unsigned long sequence와 sequence++ 확인. 멀티 스레드 적용 전 변경 필요.
- Makefile: 컴파일·링크에 -pthread가 이미 있음.
- docs/arch_procedure.md: PID + 스레드 번호 + 로컬 순번은 선택한 방향이며 미구현임을 확인.
- 코드 실행·성능 측정은 하지 않았다. 아래 항목은 구현 후 실행할 계획이며 통과 결과가 아니다.

## 구현 후 계획

| 입력·상황 | 기대 결과 | 실행 방법 |
|---|---|---|
| A 연결이 헤더 일부만 보내 대기, B는 완성 GET | 빈 워커가 있으면 B는 A 종료 전에 정상 응답 | Python socket 두 개와 동기화 이벤트로 순서 확인 |
| A가 응답 후 keep-alive 유휴, B가 GET | B는 A의 유휴 만료 전에 응답 | 실제 서버에 독립 TCP 연결 두 개 |
| N개 활성 연결 + Q개 대기 + 추가 연결 | 합의한 포화 정책, 큐/워커 상한 준수 | 작은 N/Q 설정과 처리 장벽을 사용한 재현 |
| 큐 대기로 첫 헤더 기한 경과 | 합의한 기한·만료 처리와 일치 | accepted_at 제어 및 실제 큐 대기 검증 |
| 한 연결에 연속/파이프라인 GET·POST | 응답 순서와 기존 연결 재사용 계약 유지 | 기존 persistent 테스트와 실제 서버 경유 검증 |
| 여러 워커의 업로드, 기존 ID 충돌 | ID 비중복, 파일·메타데이터 일치, 기존 파일 보존 | 병렬 POST 및 충돌 주입, 저장 바이트 대조 |
| 워커 생성 일부 실패·큐 초기화 실패 | 생성된 워커 join, FD·메모리·잠금 자원 회수 | 실패 주입 가능한 초기화 경계 테스트 |
| 대기·활성 연결이 있는 상태의 종료 | 합의한 배출/폐기·기한 준수, join 완료 | SIGTERM과 프로세스 종료 시간/FD 관찰 |
| 반복 연결·클라이언트 중도 종료 | 이중 close·FD 누수·서버 종료 없음 | 반복 socket 요청과 FD 계측 |
| 기존 HTTP 회귀 | F1 동작 유지 | make test |
| 공유 상태 경쟁 | 큐·업로드 ID 데이터 레이스 없음 | 지원 환경에서 별도 ThreadSanitizer 빌드; ASan과 분리 |

부하 측정은 동일 요청·동시 연결 수·실행 환경에서 직렬 기준과 비교한다. 처리량과 지연, 오류 수를 함께 기록하며 워커 수만으로 성능 향상을 단정하지 않는다. 기존 test_persistent의 pthread 사용은 테스트용 연결 핸들러 실행이며 제품 main의 풀을 검증하는 것은 아니다.
