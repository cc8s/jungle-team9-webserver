# F2. 멀티 스레드 설계 초안

## 목적과 범위

한 연결의 HTTP 처리·keep-alive 대기 때문에 다음 연결 처리가 지연되는 문제를 해결한다. 이번 작업은 설계와 함수 흐름 정리이며 제품 코드는 변경하지 않는다.

현재 main은 accept → 수락 시간 기록 → O_NONBLOCK 설정 → handle_connection → close를 직렬 실행한다. handle_connection 내부의 poll은 해당 연결 하나만 기다리므로 연결 간 동시성을 제공하지 않는다.

## 사용자가 결정한 방향

- 동시 연결 처리에 멀티 스레드를 사용한다.
- 기존 의사결정 기록의 업로드 ID 방향은 PID + 스레드별 고유 번호 + 스레드 로컬 순번이다. 표준 UUID는 아니며 아직 구현되지 않았다.

## 제안 구조 — 아직 합의 전

고정된 N개 pthread 워커와 크기 Q의 연결 FIFO 큐를 둔다. main은 연결 수락과 큐 전달을 담당하고 워커는 연결 하나를 종료까지 처리한다.

- 작업 항목: conn_fd와 accepted_at. main의 지역 변수 주소를 전달하지 않고 값을 큐에 복사한다.
- 동일 연결의 요청은 한 워커에서 순서대로 처리한다. 기존 버퍼·파이프라이닝 순서·타임아웃 계약을 재사용하기 쉽다.
- 워커는 연결 종료 후 다음 작업을 가져온다. 연결마다 스레드를 생성하는 비용과 무제한 스레드 증가를 피한다.
- 큐의 인덱스·개수·종료 상태만 mutex로 보호한다. 빈 큐에서는 condition variable로 기다리고 조건은 while로 재검사한다. 네트워크·파일 I/O는 잠금 밖에서 수행한다.
- FD 소유권은 큐 삽입 성공 전까지 main, 성공 후 큐, 꺼낸 뒤 워커로 이동한다. 실패한 삽입의 FD는 main이 닫고 처리 완료 FD는 워커가 한 번 닫는다.
- http_buffer·http_request·응답·JSON 데이터는 기존처럼 연결/호출 단위로 유지한다. 불변 MIME 표는 공유할 수 있다.
- 현재 store_upload의 static sequence++는 데이터 레이스를 일으킨다. 워커 번호를 시작 시 부여하고 로컬 순번으로 전환한 뒤 병렬 업로드를 허용한다. O_EXCL 충돌 재시도와 자신이 생성한 파일만 정리하는 계약은 유지한다.

## 한계

워커는 keep-alive 유휴 5초 동안에도 점유된다. N개의 느린 연결이 모든 워커를 점유하면 새 연결은 큐에서 대기한다. 이 구조는 제한된 동시성을 제공하며 대규모 유휴 연결 처리를 위한 이벤트 루프와는 처리 특성이 다르다. 메모리 사용량도 동시 활성 연결 수에 따라 증가한다.

커널 listen backlog와 애플리케이션 큐는 별개다. 현재 listen backlog는 1이며 함께 검토해야 한다. O_NONBLOCK과 기존 poll 기반 I/O는 유지하는 안이다.

## 구현 전에 합의할 사항

| 항목 | 초안 제안과 선택지 |
|---|---|
| 실행 모델 | 고정 워커 풀 권장. 연결마다 pthread 생성도 가능하나 동시 생성 수 제한 필요 |
| 크기·설정 | 학습용 출발값 N=4, Q=16 제안. 확정값·상한·CLI/상수 여부 결정 필요 |
| 큐 포화 | 새 연결 즉시 close 권장. 큐 공간 대기 또는 503도 선택 가능. 503 송신은 main을 막지 않도록 별도 기한·전송 경로 필요 |
| 첫 헤더 기한 | 기존 accept 시점부터 5초 유지 권장. 큐 대기도 포함하므로 꺼낼 때 이미 만료될 수 있음. 워커 시작 기준으로 바꾸려면 기존 정책 변경 합의 필요 |
| 만료된 대기 작업 | 기존 수신 함수에 전달할지, 워커에서 즉시 닫을지 결정 필요. 기존 함수는 이미 받은 완성 헤더를 기한 뒤에도 처리할 수 있으므로 엄격한 만료 차단과 다름 |
| backlog | 큐와 별도로 값 결정 필요. OS가 실제 크기를 제한할 수 있음 |
| 종료 | SIGINT/SIGTERM 수락 중단 → 큐 종료 통지 → 워커 join 제안. 대기 연결 배출/폐기, 활성 연결 완료/강제 종료, 전체 종료 기한 결정 필요 |
| 초기화 실패 | 일부 pthread_create 실패 시 전체 시작 취소 권장. 이미 만든 워커를 깨워 join하고 큐·소켓 정리 |
| 업로드 ID | 워커 번호·스레드 로컬 상태 전달 방식, 최종 문자열 형식·길이·순번 소진 처리 확정 필요. 재시작 충돌은 기존 O_EXCL로 검출 |

## 점진적 구현 후보

1. 큐와 풀의 초기화·실패 정리·FD 소유권을 구현하고 별도 검증한다.
2. 업로드 ID의 공유 가변 상태를 제거한다. 비워커 단위 테스트 호출 경로의 ID 상태도 정의한다.
3. main의 직접 handle_connection 호출을 큐 전달로 바꾸고 동시 연결·기존 HTTP 동작을 검증한다.
4. 합의한 종료 정책을 연결하고 포화·종료·누수 검증 후 부하를 측정한다.

정책 합의 후 각 작업 단위의 문서·구현·검증을 함께 커밋한다.
