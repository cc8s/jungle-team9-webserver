# F1. 함수 흐름

## 현재 코드의 흐름

```text
main()
  socket()
  signal(SIGPIPE, SIG_IGN)
  setsockopt()
  bind()                 ← 현재 포트 8000
  listen()
  while (1)
    accept()             ← 클라이언트 연결 FD 획득
    TODO                 ← HTTP 처리 추가 위치
    close(conn_fd)
```

현재는 HTTP 수신·파싱·응답 함수가 없다. 기존 main의 초기화와 반복문을 출발점으로 사용한다.

## 단계별 확장 계획

아래 이름은 역할 설명이며 확정된 함수명이나 파일 분할 지시가 아니다. 각 단계마다 변경 설명, 검증, 문서 갱신, 커밋을 완료한다. 다음 단계는 사용자와 진행 범위를 맞춘다.

| 단계 | 추가할 동작 | 이해·검증할 핵심 |
|---|---|---|
| 1 | TODO 위치에서 소켓 데이터 수신 | read 반환값, 수신 바이트 수, EOF와 EINTR |
| 2 | 버퍼 누적과 CRLF 경계 탐색 | 여러 read로 나뉜 행·헤더 처리 |
| 3 | 요청 라인 파싱 | 메서드·요청 대상·버전 추출, 부족과 오류 구분 |
| 4 | 헤더와 본문 길이 파싱 | Content-Length, 헤더와 본문이 함께 도착한 경우 |
| 5 | 경로 처리와 파일 접근 | 쿼리·디코딩·루트 이탈·심볼릭 링크 |
| 6 | 응답 생성과 전송 | MIME·길이·부분 전송·응답 도중 실패 |
| 7 | 시간 제한 적용 | 합의한 기한과 블로킹 방식의 관계 |

단계 1의 수신 결과 관찰은 최종 HTTP 동작이 아니다. 수신만 구현된 단계에서는 curl의 정상 응답을 기대하지 않는다.

## 최종 목표 흐름 — 아직 미구현

```text
accept()에서 conn_fd 획득
→ 수신 버퍼에 바이트 누적
→ 파서에 버퍼와 유효 길이 전달
   ├─ 추가 데이터 필요: 수신 반복
   ├─ 오류: 응답 시작 전이면 오류 응답 시도 → 정리
   └─ 완료: 요청 정보와 본문 범위 전달
→ 메서드와 경로 검증
→ 정적 파일 열기 → 파일 크기와 MIME 결정
→ 상태 라인 + 헤더 + 빈 줄 전송
→ 파일 read → 본문 write 반복
→ 파일과 버퍼 정리 → 기존 close(conn_fd)
```

## 데이터와 자원 소유권

- `conn_fd`: 현재 main이 획득하고 닫는다. 소유권을 바꿀 때는 먼저 합의한다.
- 수신 버퍼: 유효 바이트 수를 별도로 관리한다. 본문 길이는 strlen으로 계산하지 않는다.
- 파싱 필드: 버퍼 참조 또는 복사 방식은 미정이다. 참조 방식이면 버퍼 이동·해제 시점을 명확히 한다.
- 파일 FD와 파일 전송 버퍼: 해당 단계에서 수명과 정리 위치를 명시한다.
- 파일 전송 중 실패: 이미 전송한 상태 라인을 바꾸려 하지 않고 정리 경로로 이동한다.
