# F1. HTTP 처리 설계

## 목적과 현재 상태

기존 `src/main.c`의 `socket → bind → listen → accept → close` 흐름에 HTTP 기능을 작은 단계로 추가한다. 기존 코드와 주석을 유지하고 각 단계의 동작을 설명한다.

## 합의한 동작

- 수신 버퍼는 응답 처리 완료까지 유지하고 연결 정리 시 해제한다. 중간 flush나 버퍼 압축은 하지 않는다.
- GET은 헤더 검증 후 본문을 기다리지 않는다. POST는 Content-Length만큼 수신하며 헤더 완료부터 10초 전체 기한을 적용한다.
- consumed는 GET 등 본문을 사용하지 않는 메서드에서 헤더 길이, POST에서 헤더 길이 + Content-Length다. 무시한 본문과 후속 바이트는 연결 종료 시 버린다.

- 수신 버퍼는 4 KiB로 시작해 필요할 때 확장한다. 요청 라인 8 KiB, 전체 헤더(요청 라인 포함) 32 KiB, 본문 1 MiB를 상한으로 둔다.

- 현재 코드는 HTTP/1.1 GET 정적 파일 응답과 POST 본문 수신까지 구현돼 있다. 다음 구현 목표는 아래 POST 확장 계약이며, 문서 갱신만으로 POST 처리가 구현된 것은 아니다.
- 연결당 첫 요청만 처리하고 Connection: close로 응답한 뒤 연결을 닫는다. 후속 요청은 처리하지 않는다.
- 구현·검증·커밋 단위는 A: HTTP request 파싱, B: HTTP response 생성·쓰기로 나눈다.

- 수신 버퍼와 파서를 분리한다. 수신 데이터를 누적하고 수신 직후 파서에 전달한다.
- 파서는 `추가 데이터 필요 / 완료 / 오류`를 구분한다. 요청 처리 중에는 버퍼를 유지하고 처리 후 정리한다.
- 요청 라인에서 메서드, 요청 대상, HTTP 버전을 추출한다.
- 행은 CRLF, 헤더 끝은 CRLF 두 개로 구분한다. 헤더 끝을 요청 전체의 끝으로 취급하지 않는다.
- 본문은 Content-Length 바이트만큼 처리한다. 본문에는 NUL 바이트와 CRLF가 들어갈 수 있다.
- 경로는 쿼리 분리 → 한 번 디코딩 → 검증 순서로 처리한다. 전체 하위 경로를 유지한다.
- 정적 루트 밖 접근과 중간 디렉토리를 포함한 심볼릭 링크를 차단한다.
- GET 정적 파일 처리에 POST JSON·폼 해석과 Base64 파일 저장을 추가할 예정이다. CGI와 프록시 라우팅은 이후 범위다.
- 응답 MIME 타입은 실제 제공할 파일의 확장자로 결정한다.
- 상태 라인과 헤더를 한 버퍼에 구성하고 빈 줄 뒤에 본문을 전송한다. Content-Length는 본문의 바이트 수다.
- 부분 읽기·쓰기를 처리하고 EINTR로 중단된 I/O는 재시도한다. 종료 의도가 있으면 정리한다.
- 응답 시작 전 실패는 오류 응답으로 처리한다. 응답 도중 실패는 새 오류 응답을 덧붙이지 않고 정리한다.
- 연결 FD, 열린 파일 FD, 동적 할당 버퍼를 모든 종료 경로에서 정리한다.

## A 구현 결과

- `src/http_request.h`와 `src/http_request.c`에 수신과 파서를 분리했다.
- 파싱 필드는 수신 버퍼의 오프셋·길이로 저장한다. 버퍼 확장 후에도 유효하다.
- 잘못되거나 중복된 Content-Length는 `HTTP_BAD_REQUEST`, 본문 상한 초과는 `HTTP_BODY_TOO_LARGE`로 반환한다.
- Transfer-Encoding 단독은 `HTTP_UNSUPPORTED_TRANSFER`, Content-Length와 병용은 `HTTP_BAD_REQUEST`다.
- 파싱·수신 오류는 HTTP 상태 코드가 아닌 오류 종류로 B에 전달한다.
- HTTP/1.1 요청 라인과 필수 Host의 존재·중복·기본 형식을 검증한다. Host의 상세 문법 검증은 후속 보완 사항이다.
- 파서는 메서드를 추출한다. GET 이외 메서드의 405 응답은 B의 책임이다.
- sock_fd는 블로킹, accept로 수락한 conn_fd는 O_NONBLOCK으로 설정한다. 헤더·본문 수신 기한은 poll(POLLIN)과 recv(..., 0)으로 적용한다.
- main은 A 결과를 B에 전달하고, B가 끝난 뒤 버퍼를 해제하고 연결을 닫는다.

## 헤더 수신 타임아웃 보완

- accept 성공 직후 단조 시계로 현재 시간을 기록하고 절대 기한을 5초 뒤로 정한다.
- A의 `http_receive_request()`에 기한을 전달한다. 헤더 수신 중에는 poll에 남은 시간만 전달하며 부분 수신·EINTR로 기한을 연장하지 않는다.
- poll 이후에는 논블로킹 conn_fd에 recv(..., 0)를 호출한다. EAGAIN/EWOULDBLOCK이면 같은 절대 기한으로 다시 대기한다.
- 기한 안에 CRLF 두 개까지 수신되지 않으면 HTTP_HEADER_TIMEOUT을 반환한다. B가 이후 408 응답을 담당한다.
- 이번 보완은 헤더 기한만 포함한다. 이후 본문 수신 기한은 아래 정책 변경에서 구현했다.

## B 구현 결과와 확정 정책

- 정적 루트는 실행 디렉토리의 www다. `/`는 index.html로 매핑하고 그 외 디렉토리는 403으로 처리한다.
- 쿼리 분리 → 경로 디코딩 → 검증 후 openat/O_NOFOLLOW로 각 경로 요소를 연다. 중간·최종 심볼릭 링크와 모든 `..` 요소를 차단한다.
- open 시 O_NONBLOCK은 FIFO 등 비정규 파일에서 대기하지 않기 위한 파일 옵션이다. 최종 FD는 fstat으로 일반 파일인지 확인한다.
- MIME은 파일 확장자로 결정한다. HTML/CSS/JS/JSON/PNG/JPG/JPEG 외에는 application/octet-stream이다.
- 요청 오류 400, 접근 차단 403, 파일 없음 404, 비GET 405와 Allow: GET, 헤더 시간 초과 408, 본문 과대 413, 요청 라인 과대 414, 헤더 과대 431, 내부 오류 500, 전송 코딩 미지원 501, 버전 미지원 505를 적용한다.
- 상태 라인·헤더를 한 버퍼로 전송하고 파일을 16 KiB씩 읽어 선언한 길이까지만 전송한다. 1 KiB 강제 분할 없이 최대 16 KiB 청크의 남은 바이트를 send(..., 0)에 전달하고, 반환한 바이트 수만큼 위치를 이동한다. 오류 응답도 길이가 명시된 본문을 가진다.
- 마지막 실제 send 성공 이후 5초간 전송 진전이 없으면 실패를 반환한다. 논블로킹 conn_fd에서 poll(POLLOUT)과 send(..., 0)를 사용한다. EAGAIN/EWOULDBLOCK은 기한을 연장하지 않고, 양수 반환만 진행으로 본다.
- 응답 중 실패하면 새 오류 응답을 붙이지 않는다. B가 파일 FD를 닫고, main이 수신 버퍼와 연결 FD를 정리한다.
- 본문 수신 제한은 이후 A의 정책 변경에서 구현했다.

## 본문 정책 변경 및 10초 제한

- GET을 포함한 비POST 메서드는 헤더 검증 후 COMPLETE를 반환한다. 잘못된 Content-Length·Transfer-Encoding 검증과 상한 검사는 유지한다.
- POST만 본문을 기다린다. 헤더 파싱 완료 시 단조 시계로 10초 뒤의 절대 기한을 한 번 설정하고 poll/recv에 적용한다. 부분 수신·EINTR·EAGAIN은 기한을 연장하지 않는다.
- 헤더와 본문이 함께 수신됐거나 본문 길이가 0이면 추가 대기 없이 완료한다.
- HTTP_BODY_TIMEOUT은 B에서 408로 변환한다. 파싱에 성공한 POST는 현재 B에서 405로 응답한다. POST 애플리케이션 처리는 여전히 미지원이다.

## 소켓 모드 계약 변경

- 이 설계가 현재 계약이며 f1_draft.md의 초기 블로킹 I/O 설명은 과거 초안이다.
- accept 직후 시간을 기록하고 기존 FD 플래그를 보존하여 conn_fd에 O_NONBLOCK을 추가한다. 설정 실패 시 해당 연결만 닫고 다음 accept로 진행한다.
- main은 리스닝 소켓의 블로킹 모드를 유지한다. A/B 함수의 호출자는 논블로킹 연결 FD를 전달해야 한다.
- 송신 버퍼 여유 공간은 미리 계산하지 않는다. poll의 준비 알림 이후에도 부분 전송과 EAGAIN이 가능하므로 반환값으로 처리한다.
- 헤더 5초·POST 본문 10초는 고정 기한이고, 쓰기 5초는 실제 전송 진전 시 갱신한다. GET 본문 생략과 POST의 최종 405 정책은 유지한다.

## 2-1〜2-3 보완 계약

- recv 이후에는 EINTR/EAGAIN 등 재시도, 실제 오류, EOF, 수신 길이 누적 순서로 결과를 처리한다. 성공한 바이트를 반영하기 전에 기한 초과로 버리지 않는다. 재대기 기한은 wait_for_data에서 검사한다.
- 현재 수신된 헤더 영역의 문법 오류를 길이 오류보다 우선한다. 완성된 헤더는 요청 라인·헤더 필드 문법을 검증한 뒤 길이 제한을 판정한다. 불완전 헤더는 현재 가능한 검사 뒤에 길이를 판정한다.
- 수신 단계에서 헤더 누적량을 32 KiB로 제한한다. 이후 도착할 미수신 바이트의 문법 오류까지 기다리지는 않는다. 이미 수신된 헤더 뒤의 바이너리 본문은 문법 검사에서 제외한다.
- 요청 라인과 헤더의 상한은 CRLF를 포함한다. 상한 안에 종료 경계가 완성되면 허용하고, 경계 없이 상한까지 차면 오류다.
- http_send_response는 오류 응답 경로를 먼저 처리한다. 정상 요청 필드의 offset/length는 buffer.length 범위인지 뺄셈 방식으로 검사한 뒤 접근한다. 잘못된 내부 구조체·필수 인자 누락은 500이다.
- 유효한 버퍼 범위 안에 있는 요청 대상 길이가 8 KiB 이상이면 414다. 범위 오류와 길이 초과가 함께 있으면 내부 오류 500으로 처리한다.
- decode_path는 출력 크기를 받아 디코딩 문자·NUL 종료·index.html 치환의 공간을 확인한다. 공간 부족은 414다.

## POST 확장 계약 — 설계 확정, 아직 미구현

### 목적과 지원 범위

기존 A의 본문 수신과 B의 응답 생성·전송 함수를 재사용한다. JSON 파서는 C로 직접 구현한다. JSON·URL 인코딩 폼을 해석하고 결과를 반환하며, 파일은 클라이언트가 Base64로 인코딩한 JSON을 전송한다. multipart 파서는 이번 범위에서 제외한다.

사용자 데이터의 영구 저장은 제외한다. 파일 업로드에 한해서는 Base64 디코딩 결과를 저장한다. 기존의 비GET 일괄 405는 현재 코드의 동작이며, 확장 후 아래 경로별 정책으로 대체한다.

### 경로와 요청 자료형

경로는 쿼리 분리 → 한 번 디코딩 → 검증 후 비교한다. 예약 API 경로를 정적 파일보다 먼저 분기한다.

| 경로 | 허용 메서드 | 요청 Content-Type | 성공 응답 |
|---|---|---|---|
| /api/users | POST | application/json, 최상위 객체 | 200, 해석한 사용자 데이터 |
| /api/form | POST | application/x-www-form-urlencoded | 200, 해석한 키·값 |
| /api/upload | POST | application/json, Base64 업로드 객체 | 201, 저장 식별자·원본 파일명·디코딩된 바이트 수 |

- 예약 API 경로의 다른 메서드는 405와 Allow: POST다.
- 그 외 POST 경로는 404, 기존 정적 파일 경로는 GET을 허용한다.
- 지원하지 않는 메서드에 대한 Allow 값은 해당 경로에 맞춰 생성한다. 기존 Allow: GET 고정값을 일반화한다.
- 양수 본문의 Content-Type 누락 또는 해당 경로가 받지 않는 타입은 415다. multipart/form-data도 현재 미지원 타입이다.

### 요청 헤더와 본문 수신

- POST는 Content-Length 헤더가 없으면 본문 수신을 기다리지 않고 411 Length Required를 반환한다.
- 헤더 누락과 명시적 0을 구분하도록 has_content_length를 보관한다. Content-Type은 기존 필드처럼 오프셋·길이로 보관한다.
- 명시적인 Content-Length: 0은 허용한다. 존재하는 POST API 경로에서는 타입별 파서를 건너뛰고 200과 `{"ok":true,"data":null}`을 반환한다. 업로드 경로도 이 경우 파일을 만들지 않는다.
- 잘못되거나 중복된 Content-Length는 400, Transfer-Encoding과 병용은 400, 단독 Transfer-Encoding은 기존대로 501이다. 이 충돌·문법 검증을 누락 길이 411보다 먼저 수행한다.
- 본문 상한 1 MiB는 Base64와 JSON 메타데이터를 포함한 수신 바이트 전체에 적용한다. 디코딩 파일만의 1 MiB 제한이라는 뜻이 아니다.
- 헤더 완료부터 본문 수신 전체 10초, 전송 진행 없는 5초, 연결당 첫 요청 후 종료 정책은 유지한다.

### JSON·폼 복잡도 제한

| 항목 | 제한 |
|---|---:|
| JSON 중첩 깊이 | 16단계, 최상위 객체·배열을 1단계로 계산 |
| 객체별 필드 | 100개 |
| 배열별 원소 | 1,000개 |
| 요청 전체 JSON 값 | 10,000개, 컨테이너와 하위 값 포함, 객체 키 자체는 제외 |
| URL 인코딩 폼 필드 | 100개 |
| 수신 본문 전체 | 1 MiB |

JSON은 객체·배열·문자열·숫자·불리언·null 및 중첩 구조를 지원한다. 문법 오류와 중복 JSON 키는 400, 복잡도·크기 상한 초과는 413이다. 중복 키는 이스케이프를 해석한 실제 키 기준으로 판별한다. JSON 문자열은 디코딩된 UTF-8 바이트와 길이로 보관하며 NUL 종료에 의존하지 않는다. URL 인코딩 폼은 키·값 분리, %XX 디코딩과 +의 공백 변환을 수행한다. 디코딩된 필드명이 중복되면 400으로 거절한다.

### Base64 업로드와 바이트 보존

요청 예시:

```json
{
  "filename": "photo.png",
  "content_type": "image/png",
  "encoding": "base64",
  "data": "iVBORw0KGgo..."
}
```

예시의 data는 설명용 축약이며 실제 요청에는 완전한 Base64 문자열을 넣는다. 외부 Content-Type: application/json은 전송 형식이고, JSON의 content_type은 원본 파일의 메타데이터다.

- filename, content_type, encoding, data를 해석한다. encoding은 base64다. 필수 필드 누락·타입 오류·잘못된 Base64는 400으로 처리한다.
- 디코딩 바이트를 변환·문자열 처리 없이 그대로 보존한다. NUL과 CRLF도 파일 바이트에 포함된다.
- 파일 확장자나 content_type으로 내용을 변환하거나 실제 파일 형식을 판정하지 않는다. 형식 검증은 별도 기능이다.
- 저장 위치는 실행 디렉토리의 uploads_storage/다. www/ 밖에 두며 GET 정적 파일 서빙에 연결하지 않는다.
- 저장 파일명은 현재 시각을 기준으로 서버가 생성한다. 같은 식별자의 `<ID>.bin`에 원본 바이트를, `<ID>.json`에 원본 파일명·타입·디코딩 바이트 수를 보관한다. 클라이언트 filename은 메타데이터이며 저장 경로에 사용하지 않는다.
- uploads_storage/는 미리 존재한다고 가정한다. 서버 시작 시 자동 생성하지 않는다. 업로드 시 디렉토리 접근·파일 생성·쓰기 실패는 500으로 처리한다.
- 두 파일은 쓰기용 FD로 생성·기록한 뒤, 저장 완료 시 모두 0400으로 설정한다. 서버 실행 사용자만 읽을 수 있고 그룹·다른 사용자에게는 권한을 부여하지 않는다. 권한 변경 실패도 저장 실패로 처리한다.
- 두 파일의 기록과 권한 설정이 모두 성공해야 저장 성공이다. 한쪽만 만들어진 상태에서 실패하면 이번 요청이 생성한 두 파일을 정리한다. 기존 파일은 삭제하거나 덮어쓰지 않는다.
- Base64는 일반 알파벳 A–Z/a–z/0–9/+/를 허용하고 필요한 끝자리 = 패딩을 요구한다. 공백·줄바꿈과 URL용 -/_는 거절한다. 잘못된 입력은 400이며 저장 파일을 생성하지 않는다.
- 기존 파일을 덮어쓰지 않는다. 디코딩·쓰기 실패 시 새로 만든 불완전 파일을 삭제하며, 생성·쓰기·정리 과정의 FD와 메모리를 회수한다.
- 전체 저장에 성공한 뒤에만 201 Created로 응답한다. 응답 전송 실패만으로 이미 정상 저장된 파일을 불완전 파일로 간주하지 않는다.

### 공통 JSON 응답

POST API 성공·오류 응답의 Content-Type은 application/json으로 한다. GET의 기존 MIME 응답은 유지한다.

```json
{"ok":true,"data":{"name":"홍길동","age":25}}
```

```json
{"ok":true,"data":{"id":"서버가 생성한 식별자","filename":"photo.png","size":12345}}
```

```json
{"ok":false,"error":{"code":"invalid_json","message":"Invalid JSON body"}}
```

응답 예시의 식별자·오류 코드 문자열은 형태 예시다. 사용자 문자열은 JSON 이스케이프 후 출력하고 Content-Length는 UTF-8 직렬화 결과의 바이트 수로 계산한다. 요청 본문을 JSON 문자열로 무검증 연결하지 않는다.

POST 확장에서 추가하는 상태는 201(저장 성공), 411(명시적 길이 누락), 415(미지원 본문 타입)다. 기존 400/404/405/408/413/500 오류 정책과 전송 도중 추가 오류 응답 금지는 유지한다.

### 구현 전에 구체화할 세부 사항

- 현재 시각 기반 ID의 정확한 형식·시간 정밀도·충돌 재시도 방식. 시각이 같거나 시계가 변경돼도 기존 파일을 덮어쓰지 않아야 한다.
- 두 파일의 생성·권한 변경·정리를 수행할 구체적인 시스템콜과 메타데이터 JSON 필드명.
- JSON 숫자의 내부 표현과 유니코드 검증 세부 구현. 문자열의 UTF-8 바이트·길이 보관 정책은 확정됐다.
- Content-Type 매개변수·중복 헤더 처리. 중복 폼 필드의 400 거절은 확정됐다.
- 파일 저장 성공 후 응답 실패 시 클라이언트 재시도의 중복 업로드 처리.

세부 구현을 문서 갱신만으로 임의 확정하지 않는다. 이번 작업은 POST 설계 문서 갱신이며 코드 변경이 아니다.
