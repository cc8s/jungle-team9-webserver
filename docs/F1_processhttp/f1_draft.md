# F1. HTTP 요청 파싱 및 응답 처리 설계

## 1. 목적과 구현 범위

`docs/phase.md`의 HTTP 요청 파싱, 응답 생성, 정적 파일 서빙 요구사항을 단계적으로 구현한다.

- C 표준 라이브러리와 POSIX API를 사용한다.
- 초기 구현은 블로킹 I/O, 연결당 요청 하나, 정적 파일 GET 응답으로 제한한다.
- 모든 응답에 `Connection: close`를 넣고 처리 후 연결을 종료한다.
- POST 본문 파싱 구조는 마련하되, 현재 정적 파일 처리에서는 GET 이외 메서드에 `405 Method Not Allowed`와 `Allow: GET`을 반환한다.
- 동적 처리, CGI, 프록시 라우팅, keep-alive는 이후 확장한다.

## 2. 전체 처리 흐름

```text
accept()
→ 수신 버퍼 생성
→ read()로 데이터 누적
→ 요청 파서 호출
   ├─ 추가 데이터 필요: 수신 반복
   ├─ 오류: 오류 응답 후 정리
   └─ 완료: 메서드와 경로 검증
→ 정적 파일 열기 및 메타데이터 확인
→ 상태 코드, MIME 타입, 본문 길이 결정
→ 상태 라인 + 헤더 + 빈 줄 전송
→ 파일 본문을 읽어 전송
→ 파일 FD, 버퍼, 연결 FD 정리
```

메서드가 현재 지원 범위 밖임을 헤더 파싱 시 확인하면 본문 수신을 기다리지 않고 `405` 응답 후 연결을 닫을 수 있다. 연결을 재사용하지 않으므로 남은 요청 본문을 비울 필요는 없다.

## 3. 수신 버퍼 -> 파서

### 수신 처리

- 소켓 읽기와 HTTP 파싱을 분리한다. 파서는 직접 `read()`하지 않는다.
- TCP는 바이트 스트림이므로 한 번의 `read()`와 HTTP 행 또는 요청 경계는 일치하지 않는다.
- 수신 직후마다 버퍼 뒤에 데이터를 추가하고 파서를 호출한다.
- 초기에는 요청 전체를 하나의 버퍼에 누적하며 크기 제한 안에서만 확장한다.
- 헤더와 본문이 한 번에 도착할 수 있으므로 헤더 파싱 후 버퍼를 비우지 않는다.
- 요청 처리 완료 후 버퍼를 해제한다. 별도의 flush는 필요 없다.
- 요청 필드가 버퍼 내부를 참조한다면 처리 완료까지 버퍼를 유지한다. 버퍼 재할당으로 참조가 무효화되지 않도록 오프셋을 사용하거나 필드를 복사한다.

### 파서 결과

파서는 다음 상태와 소비한 바이트 수를 반환한다.

| 결과 | 의미 | 호출자 동작 |
|---|---|---|
| NEED_MORE | 유효성 오류는 없지만 데이터가 부족함 | 추가 수신 |
| COMPLETE | 요청 전체가 준비됨 | 요청 처리 |
| ERROR | 형식 오류 또는 제한 위반 | 해당 오류 응답 후 종료 |

헤더 파싱 완료 여부도 호출자가 확인할 수 있게 하여 본문 길이 확인, 메서드 검사, 본문 타임아웃 시작에 사용한다. 파싱 오류와 단순 수신 부족을 구분한다.

## 4. 요청 파싱

### 요청 라인과 헤더

- 각 행의 구분자는 `\r\n`이다.
- 첫 행에서 메서드, 요청 대상, HTTP 버전을 추출한다.
- 다음 행부터 빈 줄 전까지 헤더를 파싱한다.
- `\r\n\r\n`은 헤더의 끝이며 요청 전체의 끝을 뜻하지 않는다.
- 헤더 이름은 대소문자를 구분하지 않는다.
- HTTP/1.1을 초기 지원 버전으로 두고 `Host`를 검증한다.
- `Host`, `Content-Length`, `Connection`, `Transfer-Encoding` 등 처리에 필요한 헤더를 보관한다.
- C 문자열 함수에 의존하기 전에 수신 길이와 필드 경계를 확인한다. 파일과 본문 데이터는 바이너리일 수 있다.

### 본문 길이

- 헤더 종료 직후부터 본문으로 취급하며 줄 단위로 파싱하지 않는다.
- `Content-Length`는 본문의 바이트 수다.
- `Content-Length`와 `Transfer-Encoding`이 모두 없으면 요청 본문 길이는 0이다.
- 초기에는 `Content-Length` 방식만 지원한다.
- `Content-Length`의 음수, 비숫자 값, 정수 범위 초과, 중복은 `400`으로 거절한다.
- `Transfer-Encoding`과 `Content-Length`가 함께 있으면 `400`으로 거절한다.
- 지원하지 않는 `Transfer-Encoding`은 `501`로 거절하고 연결을 닫는다.
- 본문 길이가 제한을 넘으면 본문 전체를 받기 전에 `413`으로 거절한다.
- 길이 계산 시 정수 오버플로우를 검사한다.

```text
요청 완료 조건 = 수신 바이트 수 >= 헤더 종료 위치 + Content-Length
```

수신 버퍼에 다음 요청의 바이트가 함께 들어와도 현재 요청 길이까지만 소비한다. 초기에는 응답 후 연결을 닫으므로 후속 요청을 처리하지 않는다.

## 5. URI와 정적 파일 경로

처리 순서는 다음으로 고정한다.

1. 요청 대상에서 쿼리를 분리한다.
2. 경로의 `%XX`를 한 번 디코딩한다.
3. 경로를 검증하고 정적 루트 안의 파일로 연결한다.

예: `/css/main.css?v=1` → `/css/main.css` → `<static_root>/css/main.css`.

- 마지막 파일명만 추출하지 않고 전체 하위 경로를 유지한다.
- `/`는 `index.html`로 매핑한다. 그 외 디렉토리 목록은 제공하지 않는다.
- 잘못된 `%XX`와 디코딩된 NUL 문자는 `400`으로 거절한다.
- 디코딩 이후 `..` 등의 경로 요소를 검사해 루트 밖 접근을 차단한다.
- 심볼릭 링크는 최종 파일뿐 아니라 중간 디렉토리에서도 차단한다.
- 경로 문자열의 단순 접두사 비교만으로 접근을 허용하지 않는다.
- 구현 시 루트 디렉토리 FD를 기준으로 각 경로 요소를 `openat()`과 `O_NOFOLLOW`로 열고, 중간 요소가 디렉토리인지 확인하는 방식을 사용한다.
- 최종 FD는 `fstat()`으로 일반 파일인지 확인한다.

## 6. 정적 파일 처리와 MIME 타입

- 요청 파싱과 파일 서빙을 분리한다. 이후 메서드·경로 기반 라우팅을 추가할 수 있게 한다.
- 현재는 GET 요청을 정적 파일 처리 함수로 전달한다.
- 파일은 `open()` 계열 호출로 열고 `fstat()`으로 종류와 크기를 확인한다.
- 전체 파일을 메모리에 올리지 않고 고정 크기 버퍼로 `read()`와 전송을 반복한다.
- 응답 `Content-Type`은 실제 제공할 파일의 확장자로 결정한다.
- 요청의 `Content-Type`은 요청 본문의 타입이며 응답 타입으로 그대로 사용하지 않는다.
- `Accept`는 클라이언트의 선호 타입이다. 초기에는 콘텐츠 협상을 구현하지 않는다.

MIME 매핑은 별도 `get_mime_type()` 함수로 둔다. C의 `switch`는 문자열을 비교하지 못하므로 `strcmp()` 기반 분기나 매핑 테이블을 사용한다.

| 확장자 | Content-Type |
|---|---|
| .html | text/html |
| .css | text/css |
| .js | text/javascript |
| .json | application/json |
| .png | image/png |
| .jpg, .jpeg | image/jpeg |
| 미등록 또는 확장자 없음 | application/octet-stream |

## 7. 응답(response) 구성과 전송

응답 바이트 순서는 다음과 같다.

```text
HTTP/1.1 200 OK\r\n
Content-Type: text/html\r\n
Content-Length: 5\r\n
Connection: close\r\n
\r\n
hello
```

- 상태 라인 → 헤더 → 빈 줄 → 본문 순서로 전송한다.
- status line과 header 를 한 버퍼로 만들고 본문을 이어 전송하기.
- `Content-Length`는 헤더를 제외한 본문의 바이트 수다. 바이너리 본문에 `strlen()`을 사용하지 않는다. 대신 fstat() 사용.
- `write()`가 일부만 전송하면 반환값만큼 위치를 이동하고 나머지를 반복 전송한다.
- `read()`와 `write()`의 `EINTR`는 재시도한다. EOF, 실제 I/O 오류, 타임아웃은 구분한다.
- `SIGPIPE`를 무시하고 소켓 쓰기 실패를 반환값으로 처리한다.
- 파일은 헤더에서 선언한 길이까지만 전송하며, 그 전에 EOF가 발생하면 불완전한 응답으로 보고 연결을 종료한다.

## 8. 제한과 타임아웃

아래 값은 로컬 테스트용 초기 정책이며 상수로 관리한다.

| 항목 | 제한 | 처리 |
|---|---:|---|
| 요청 라인 | 8 KiB | 초과 시 414 |
| 전체 헤더 — 요청 라인 포함 | 32 KiB | 초과 시 431 |
| 요청 본문 | 1 MiB | 초과 시 413 |
| 헤더 수신 전체 시간 | 5초 | 408 응답 시도 후 종료 |
| 본문 수신 전체 시간 | 10초 | 408 응답 시도 후 종료 |
| 응답 쓰기 진행 없음 | 5초 | 연결 종료 |

- 헤더 기한은 연결 수락 시점, 본문 기한은 헤더 수신 완료 시점부터 계산한다.
- 수신 기한은 데이터가 도착해도 연장하지 않는다.
- 응답 쓰기 제한은 마지막으로 실제 바이트를 전송한 시점부터 계산한다.
- 경과 시간은 단조 시계로 측정한다.
- 전체 수신 기한은 단순한 호출별 소켓 타임아웃만으로 보장되지 않는다. `poll()` 등의 대기 시간에 남은 기한을 반영하고, 실제 I/O 호출도 기한을 넘겨 블로킹되지 않게 구성한다.

## 9. 오류 응답과 자원 정리

| 상황 | 응답 |
|---|---|
| 잘못된 요청 문법·헤더·길이 | 400 Bad Request |
| 루트 외부 접근·심볼릭 링크·파일 권한 거부 | 403 Forbidden |
| 파일 또는 경로 없음 | 404 Not Found |
| 현재 허용하지 않는 메서드 | 405 Method Not Allowed + Allow: GET |
| 요청 수신 시간 초과 | 408 Request Timeout |
| 본문 크기 초과 | 413 Content Too Large |
| 요청 라인 길이 초과 | 414 URI Too Long |
| 전체 헤더 크기 초과 | 431 Request Header Fields Too Large |
| 응답 시작 전 내부 처리 실패 | 500 Internal Server Error |
| 지원하지 않는 전송 코딩 | 501 Not Implemented |
| 지원하지 않는 HTTP 버전 | 505 HTTP Version Not Supported |

오류 응답에도 상태 라인, `Content-Type`, 정확한 `Content-Length`, `Connection: close`와 짧은 본문을 포함한다. 응답 시작 여부는 일부 바이트라도 실제 전송됐는지로 판단한다.

- 응답 전송 전 실패: 가능한 경우 적절한 오류 응답을 보낸다.
- 응답 일부 전송 후 실패: 새 `500` 응답을 덧붙이지 않고 연결을 종료한다.
- 소켓 전송 실패: 추가 응답을 시도하지 않고 정리한다.
- 수신 도중 클라이언트가 연결을 끝내면 요청 완성 여부를 확인하고 정리한다.
- 모든 종료 경로에서 열린 파일 FD, 동적 할당 버퍼, 클라이언트 연결 FD를 정리한다.
- 자원 소유권은 연결 처리 함수에 모으고 공통 정리 경로를 둬 누락과 중복 해제를 막는다.

## 10. 구현 시 검증할 사례

- 요청 라인, CRLF, 헤더 종료 경계가 여러 번의 수신으로 나뉘는 경우
- 헤더와 본문이 한 번에 수신되는 경우, 본문에 NUL과 CRLF가 포함된 경우
- 잘못되거나 중복된 Content-Length, 크기 제한과 수신 기한 초과
- 쿼리가 있는 경로, 인코딩된 경로 이탈, 중간·최종 심볼릭 링크
- 정상 파일, 없는 파일, 접근 불가 파일, 바이너리 파일
- 부분 전송, EINTR, 클라이언트 연결 종료, 응답 도중 파일 읽기 실패
- 정상·오류 경로에서 파일 FD와 메모리가 모두 정리되는지 확인
