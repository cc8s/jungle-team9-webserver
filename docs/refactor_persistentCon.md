# Persistent Connection 리팩터링 설계

## 목적과 범위

현재 연결당 요청 하나를 처리한 뒤 닫는 구조를, 같은 TCP 연결에서 요청·응답을 반복하는 구조로 변경한다. 이 문서는 합의한 설계이며 아직 구현하지 않았다.

기존 HTTP/1.1 파싱, GET 정적 파일 처리, POST API·업로드, 크기 제한과 오류 정책을 재사용한다. 리스닝 소켓은 블로킹, 클라이언트 소켓은 O_NONBLOCK을 유지한다. 이번 범위는 연결 재사용이며 연결 간 동시성·요청 병렬 처리는 제외한다.

## 확정한 정책

- HTTP/1.1 연결은 기본 유지한다. 유지할 응답에는 Connection 헤더를 생략한다.
- 요청에서 Connection: close를 지정하면 응답 완료 후 종료한다.
- 모든 오류 응답 후 종료한다. 오류 응답에는 Connection: close를 명시한다.
- 응답 전송 실패는 추가 오류 응답 없이 종료한다.
- 연결당 최대 100개 요청을 처리하며 100번째 응답에 Connection: close를 명시한다.
- 요청은 수신 순서대로 처리·응답한다. 여러 요청이 함께 들어와도 병렬 처리하지 않는다.
- 수신 버퍼는 연결 단위로 유지하고, 소비한 바이트 제거에는 memmove()를 사용한다.
- 요청 구조체·오류·기한·응답 임시 메모리는 요청마다 초기화한다.
- GET은 헤더 검증 후 즉시 응답한다. 연결을 재사용할 때는 명시된 본문을 수신·폐기한 후 다음 요청을 처리한다.

HTTP/1.0 지원은 추가하지 않는다. 기존 미지원 버전 정책을 유지한다.

## 전체 흐름

```text
main
  socket → bind → listen
  accept → 수락 시각 기록 → conn_fd 논블로킹 설정
  handle_connection(conn_fd, 수락 시각)
    연결별 수신 버퍼 생성
    최대 100번 반복
      요청 구조체 초기화
      첫 요청 / 유휴 대기 / 미리 수신된 다음 요청의 기한 설정
      http_receive_request → 요청 하나 파싱
      close 요청·오류·요청 수에 따라 응답 연결 정책 결정
      http_send_response → GET/POST 처리 및 공통 전송
      오류·종료 정책·전송 실패이면 반복 종료
      GET이면 남은 본문 수신·폐기
      이번 요청의 소비 범위 제거, 다음 요청 바이트 보존
    연결별 버퍼 해제
  close(conn_fd)
```

handle_connection은 도입할 역할 이름이다. main의 기존 소켓 초기화는 유지하고, 연결 반복과 정리 책임만 분리한다. 파일 FD·JSON 트리·응답 버퍼 등은 기존 요청별 소유권을 유지한다.

## 수신 버퍼와 요청 경계

1. 응답 완료 전에는 버퍼를 이동하지 않는다. 파싱 필드와 POST 본문이 버퍼 오프셋을 참조하기 때문이다.
2. POST는 header_length + content_length까지만 현재 요청에 속한다. 뒤에 있는 다음 요청 바이트는 보존한다.
3. GET의 consumed는 기존처럼 헤더 길이다. 아직 남은 GET 본문을 다음 요청으로 해석하지 않는다.
4. 이번 요청과 폐기할 본문을 제거한 뒤 남은 데이터만 memmove()로 앞으로 옮긴다. 유효 길이를 갱신하고 버퍼 용량은 재사용한다.
5. 다음 요청의 완성 여부는 남아 있는 바이트로 먼저 판단한다. 이미 완성됐다면 추가 recv 없이 처리한다.
6. 크기 제한은 각 요청에 적용한다. 여러 요청을 누적한 총 바이트 수를 한 요청의 본문 길이로 취급하지 않는다.

버퍼를 요청마다 free하거나, 이번 요청 뒤에 온 바이트를 함께 버리지 않는다. 잘못된 문법을 발견한 경우에는 재동기화를 시도하지 않고 연결을 종료한다.

## GET 본문: 응답 후 폐기

```text
GET 헤더 파싱·길이 검증
→ GET 응답 전송
→ 이미 버퍼에 온 본문부터 폐기
→ 부족한 본문만 남은 길이만큼 수신·폐기
→ 다음 요청 바이트 보존
→ 다음 요청 처리
```

- Content-Length가 없거나 0이면 폐기 단계 없이 진행한다.
- 양수이면 정확히 그 길이만 제거한다. 바이너리·NUL·CRLF를 해석하지 않는다.
- 이미 수신된 바이트 중 본문 길이를 넘는 부분은 다음 요청이다. 초과 폐기하지 않는다.
- 추가 수신은 폐기에 필요한 남은 길이 이하로 제한할 수 있다. 버퍼 관리 방식과 무관하게 다음 요청 데이터는 보존해야 한다.
- 폐기 시작부터 전체 10초의 절대 기한을 적용한다. 부분 수신·EINTR·EAGAIN으로 연장하지 않는다.
- 이미 본문 전체가 버퍼에 있으면 즉시 폐기한다.
- 폐기 중 시간 초과·EOF·I/O 오류는 연결 종료로 처리한다. 이미 GET 응답을 보냈으므로 408 등 두 번째 응답을 붙이지 않는다.
- close 요청, 오류 응답, 100번째 응답 등 종료가 결정된 경우에는 재사용을 위한 본문 폐기를 기다리지 않는다.

이 정책은 기존 GET 본문을 무시하는 애플리케이션 동작을 유지하면서 TCP 스트림의 요청 경계를 보존한다.

## Connection 헤더와 응답 결과

Connection 값은 대소문자를 구분하지 않는 쉼표 구분 토큰으로 처리한다. 예를 들어 `keep-alive, CLOSE`에도 종료를 적용한다. 여러 Connection 헤더가 있으면 모든 값에서 close 여부를 확인해야 하며 마지막 헤더로 덮어쓰지 않는다.

헤더 작성 전에 종료 정책이 정해져야 한다. 연결 계층은 클라이언트 close와 요청 수 상한을 전달하고, 응답 계층은 GET/POST 처리에서 발견한 오류에도 종료를 적용한다.

| 상황 | 응답 Connection | 응답 이후 |
|---|---|---|
| 정상 처리, 재사용 가능 | 생략 | GET 본문이 있으면 폐기 후 다음 요청 |
| 요청이 close 지정 | close | 연결 종료 |
| 100번째 요청 | close | 연결 종료 |
| 파싱·라우팅·처리 오류 응답 | close | 연결 종료 |
| 응답 도중 전송 실패 | 이미 보낸 헤더 유지 | 추가 응답 없이 연결 종료 |

http_send_response의 기존 0/-1만으로는 성공적으로 전송한 오류 응답과 정상 응답을 구분할 수 없다. 반환 결과에는 최소한 전송 성공 여부와 연결 종료 필요 여부를 포함하도록 확장한다. 구체적인 구조체·인자 이름은 구현 시 정하되, GET/POST의 모든 오류 경로가 종료 결정을 전달해야 한다.

모든 정상 응답은 기존처럼 정확한 Content-Length를 제공한다. 청크 전송·연결 종료를 이용한 본문 길이 판별은 추가하지 않는다.

## 시간과 요청 수 제한

| 구분 | 제한 | 시작 시점 | 만료 시 처리 |
|---|---:|---|---|
| 첫 요청 헤더 | 5초 | accept 성공 직후 | 408 응답 시도 후 종료 |
| 다음 요청 유휴 대기 | 5초 | 이전 요청 처리 완료 후 다음 요청을 기다릴 때 | 응답 없이 종료 |
| 다음 요청 헤더 | 5초 | 유휴 이후 첫 바이트 수신 시점 | 408 응답 시도 후 종료 |
| 이미 버퍼에 있는 다음 요청 헤더 | 5초 | 해당 요청 처리 시작 시점 | 408 응답 시도 후 종료 |
| POST 본문 | 10초 | 헤더 완료 | 408 응답 시도 후 종료 |
| GET 응답 후 본문 폐기 | 10초 | 응답 완료 후 폐기 시작 | 추가 응답 없이 종료 |
| 응답 쓰기 진행 없음 | 5초 | 쓰기 시작 또는 마지막 실제 전송 | 추가 응답 없이 종료 |
| 연결당 요청 수 | 100개 | 첫 요청부터 계산 | 100번째 응답에 close 명시 후 종료 |

- 헤더·본문·폐기는 단조 시계의 고정 기한이다. 쓰기 기한만 실제 양수 send 반환 시 갱신한다.
- 일반 요청은 응답 완료·요청 버퍼 정리 후 유휴 상태로 진입한다. GET 본문 폐기가 필요한 경우에는 폐기를 마친 후 진입한다.
- 버퍼에 다음 요청 데이터가 있으면 유휴 대기 없이 해당 요청 처리를 시작한다. 기존 수신 시각을 추적해 기한을 소급하지 않는다.
- 클라이언트가 아무 다음 요청도 보내지 않은 유휴 상태와, 요청을 시작했지만 완성하지 못한 상태를 구분한다.
- 유휴 중 정상 EOF는 응답 없이 종료한다. 요청 중 EOF는 기존 불완전 요청 정책에 따라 가능한 오류 응답을 시도한 후 종료한다. 응답을 이미 보낸 GET 본문 폐기 단계의 EOF에는 추가 응답하지 않는다.

## 구현 순서

1. 기존 요청·응답 인터페이스에 연결 유지·종료 판단과 요청별 상태 초기화 책임을 반영한다.
2. main에서 연결 처리 함수를 추출하고 연결 단위 버퍼·최대 요청 수를 관리한다.
3. 요청 소비 범위와 memmove 정리를 연결하고 일괄 수신한 다음 요청을 보존한다.
4. GET 응답 후 본문 폐기와 10초 기한을 추가한다.
5. 유휴·다음 헤더 기한 및 Connection 토큰 처리를 연결한다.
6. 기존 GET/POST 테스트를 유지하고 연결 종료에 의존하던 테스트 수신기를 Content-Length 기반으로 바꾼다.
7. 아래 검증과 F1 문서 갱신 후 작업 단위 커밋으로 롤백 지점을 남긴다.

이 목록은 구현 계획이며 이번 문서 작성에서 코드를 수정하지 않는다.

## 이번 범위의 한계

현재 서버는 연결을 순차 처리한다. 한 유지 연결의 요청 처리·유휴 대기 중에는 다른 연결의 accept 처리가 지연된다. 논블로킹 I/O와 poll을 사용하더라도 연결을 한 번에 하나만 관리하므로 다중 연결 이벤트 루프가 되는 것은 아니다. 연결 간 동시 처리는 다음 단계로 분리한다.
